## 1. 大模型参数量与推理激活参数量

### 1.1 参数量级分类

大模型的参数规模横跨数个数量级，不同量级对应不同的能力天花板和硬件需求：

| 量级 | 参数量范围 | 典型模型 | 最低显存需求（FP16） | 典型应用场景 |
|------|-----------|---------|-------------------|-------------|
| 小型（Small） | 1B–3B | Qwen2.5-1.5B, Phi-3-mini, Gemma-2B | 2–6 GB | 端侧推理、文本分类、简单问答 |
| 中型（Medium） | 7B–14B | LLaMA-3-8B, Qwen2.5-7B/14B, Mistral-7B, DeepSeek-V2-Lite | 14–28 GB | 通用对话、代码补全、文档摘要 |
| 大型（Large） | 30B–72B | Qwen2.5-32B/72B, LLaMA-3-70B, DeepSeek-V2, Mixtral 8×22B | 60–144 GB | 复杂推理、长文本理解、专业问答 |
| 超大型（Extra-Large） | 100B–400B | LLaMA-3-405B, DeepSeek-V3 (671B Total) | 200–800 GB | 最复杂推理、多模态融合、研究级任务 |
| 巨型（Massive） | 600B+ | DeepSeek-V3-671B, Qwen3-235B-MoE, GPT-4 规模等价开源模型 | 数百GB–数TB | 顶尖综合能力、通用人工智能研究 |

### 1.2 参数量存储原理

模型参数在显存中的占用取决于数值精度，每种精度对应不同的字节数：

| 精度格式 | 每参数字节数 | 典型用途 | 精度损失 |
|---------|------------|---------|---------|
| FP32（float32） | 4 bytes | 训练、严格推理 | 无损失（基准） |
| FP16（float16） | 2 bytes | 推理、混合精度训练 | 极低 |
| BF16（bfloat16） | 2 bytes | 推理（动态范围优于FP16） | 极低 |
| FP8（float8, E4M3/E5M2） | 1 byte | H100/5090 原生推理 | 低 |
| INT8 | 1 byte | 量化推理 | 低–中 |
| INT4 | 0.5 bytes | 极端压缩推理 | 中 |

**显存占用基础公式：**

```
模型权重显存(GB) = 参数量(B) × 每参数字节数
```

例如：
- LLaMA-3-8B FP16: `8 × 2 = 16 GB`
- Qwen2.5-72B INT4: `72 × 0.5 = 36 GB`
- DeepSeek-V3-671B FP8: `671 × 1 = 671 GB`

### 1.3 稠密模型（Dense）与混合专家模型（MoE）

混合专家模型（Mixture of Experts, MoE）通过稀疏激活机制，在总参数量极大的情况下控制每次推理的计算量：

```
Dense 模型: 总参数 = 激活参数（每次前向传播使用全部参数）
MoE 模型:   总参数 >> 激活参数（每次仅激活部分专家）
```

**主流 MoE 模型参数量对比：**

| 模型 | 总参数量 | 激活参数量 | 专家数 | 每次激活专家数 | 激活比例 |
|------|---------|-----------|--------|-------------|---------|
| Mixtral 8×7B | 46.7B | ~12.9B | 8 | 2 | 27.6% |
| Mixtral 8×22B | 141B | ~39B | 8 | 2 | 27.7% |
| DeepSeek-V2 | 236B | 21B | 160 | 6 | 8.9% |
| DeepSeek-V3 | 671B | 37B | 256 | 8 | 5.5% |
| Qwen3-235B-MoE | 235B | 22B | 128 | 8 | 9.4% |
| LLaMA-4-Maverick | 400B | 17B (active) | 128 | 4 | 4.25% |

**MoE 推理显存计算的特殊性：**

```
MoE 模型显存需求 = 总参数量 × 量化字节数 + KV Cache + 开销
（虽然激活参数少，但所有专家权重必须驻留在显存中以支持动态路由）
```

这意味着 MoE 模型在推理时需要加载全部参数到显存中，所以 671B 的 DeepSeek-V3 即使在 INT4 量化下也至少需要约 335 GB 显存。

### 1.4 推理总显存计算公式

完整的推理显存占用由三部分组成：

```
总显存(VRAM) = 模型权重 + KV Cache + 运行时开销
```

**其中：**

```
模型权重(GB) = 参数量(B) × 每参数字节数

KV Cache(GB) = 2 × n_layers × n_key_value_heads × d_head × context_length × batch_size × bytes_per_elem
```

**KV Cache 计算示例（LLaMA-3-8B, FP16）：**

| 参数 | 值 |
|------|---|
| n_layers | 32 |
| n_key_value_heads | 8 (GQA) |
| d_head | 128 |
| context_length | 4096 |
| batch_size | 1 |
| bytes_per_elem | 2 (FP16) |

```
KV Cache ≈ 2 × 32 × 8 × 128 × 4096 × 1 × 2
        = 2 × 32 × 8 × 128 × 4096 × 2
        = 536,870,912 bytes
        ≈ 0.5 GB
```

当 context_length 达到 128K 时，同一模型的 KV Cache 将膨胀至约 **16 GB**。

**运行时开销（经验估算）：**

| 组件 | 估算值 |
|------|--------|
| 推理框架开销 | 权重的 5%–10% |
| 中间激活值 | batch_size × seq_len × hidden_dim × 2–4 bytes × n_layers / 1024³ |
| CUDA Context | 0.5–2 GB |
| 系统预留 | 1–3 GB |

**综合显存估算经验法则：**

```
总显存 ≈ 模型权重(GB) × 1.2 + KV Cache(GB) + 2GB
```

## 2. 量化技术概述

### 2.1 主流量化方法对比

| 量化方法 | 支持精度 | 典型压缩比 | 推理框架 | 特点 |
|---------|---------|-----------|---------|------|
| **GPTQ** | INT8, INT4, INT3 | 2–4× vs FP16 | vLLM, TGI, TensorRT-LLM | 基于 OBQ 逐层量化，需校准数据，校准后模型直接可用 |
| **AWQ** | INT4 | ~3.5× vs FP16 | vLLM, TGI, TensorRT-LLM | 保护关键权重通道（Salient Channels），比 GPTQ 质量更优 |
| **GGUF/GGML** | Q2_K–Q8_0 范围 | 2–8× vs FP32 | llama.cpp, Ollama | CPU+GPU 混合推理，K-quant 提供多级精度选择 |
| **bitsandbytes** | INT8, NF4 | 2–4× vs FP16 | HuggingFace Transformers | 推理/训练即用，NF4 为 4-bit 正态分布量化 |
| **FP8 (Native)** | FP8 (E4M3/E5M2) | 2× vs FP16 | TensorRT-LLM, vLLM | H100/H200/B200/RTX 5090 原生支持，几乎无损 |
| **AQLM** | 2-bit | ~7× vs FP16 | 专用 kernel | 基于加性量化，压缩率极高但部署复杂 |

### 2.2 量化精度级别详解（GGUF K-Quant 体系）

GGUF 格式的 K-Quant 量化是 llama.cpp 生态最常用的方案：

| 量化类型 | 每参数位宽 | 相对质量 | 推荐场景 |
|---------|-----------|---------|---------|
| **Q8_0** | 8-bit | 99.99% | 几乎无损，适用于对质量要求极严的场景 |
| **Q6_K** | 6-bit | 99.5% | 高质量推理，接近原始性能 |
| **Q5_K_M** | 5-bit | 98.5% | 平衡推荐，质量损失极小 |
| **Q4_K_M** | 4-bit | 97% | 消费级硬件最佳选择，性价比最高 |
| **Q4_0** | 4-bit | 95% | 较小模型使用 |
| **Q3_K_M** | 3-bit | 92% | 极端压缩，小参数量模型可用 |
| **Q2_K** | 2-bit | 85% | 仅推荐用于测试，质量损失明显 |

### 2.3 量化对质量的影响（Perplexity 基准）

Perplexity（困惑度）是衡量量化损失的常用指标，越低越好。以下为典型数据（WikiText-2 数据集）：

```
LLaMA-2-7B 基准 (FP16):           Perplexity = 5.47
  ├── Q8_0:                       Perplexity = 5.47  ( +0.0%)
  ├── Q6_K:                       Perplexity = 5.48  ( +0.2%)
  ├── Q5_K_M:                     Perplexity = 5.52  ( +0.9%)
  ├── Q4_K_M:                     Perplexity = 5.65  ( +3.3%)
  ├── Q3_K_M:                     Perplexity = 6.03  (+10.2%)
  └── Q2_K:                       Perplexity = 7.21  (+31.8%)
```

**经验法则：**
- **INT8 / FP8**：几乎无质量损失（<0.1%），生产环境首选
- **INT4 (GPTQ/AWQ)**：质量损失 2%–5%，消费级硬件推荐
- **3-bit 及以下**：小模型（<3B）勉强可用，大模型（>30B）容错能力更强可尝试

### 2.4 量化硬件兼容性

| GPU 架构 | FP16 | BF16 | FP8 | INT8 (Tensor Core) | INT4 (Tensor Core) | 推荐量化方案 |
|---------|------|------|-----|--------------------|--------------------|-------------|
| Turing (RTX 20 系列) | Yes | No | No | Yes (TENSOR_CORE) | Yes (TENSOR_CORE) | GPTQ INT8, GGUF |
| Ampere (RTX 30/A100) | Yes | Yes | No | Yes (TENSOR_CORE) | Yes (TENSOR_CORE) | AWQ INT4, GGUF |
| Ada Lovelace (RTX 40) | Yes | Yes | Yes (部分) | Yes (TENSOR_CORE) | Yes (TENSOR_CORE) | AWQ INT4, FP8 |
| Hopper (H100/H200) | Yes | Yes | Yes (Native FP8) | Yes (TENSOR_CORE) | Yes (TENSOR_CORE) | FP8 Native, AWQ |
| Blackwell (B100/B200) | Yes | Yes | Yes (Native FP4/FP6) | Yes | Yes (Native) | FP8/FP4 |
| Apple M 系列 | Yes (ANE) | No | No | No | No | GGUF (Metal) |

### Phase 1: 需求分析

#### 1.1 用例分析（Use Case Analysis）

在部署前必须明确以下核心问题：

| 分析维度 | 选项 | 影响 |
|---------|------|------|
| **主要用途** | 通用聊天 | 对推理速度要求适中，需 RAG 增强 |
| | 代码生成/补全 | 需低延迟（<500ms），对输出质量要求高 |
| | 长文档处理 | 需超大 KV Cache，显存需求增加 2–4× |
| | 私有知识问答（RAG） | 需额外部署 Embedding 模型和向量数据库 |
| | 微调/继续训练 | 显存需求 ×3–4（优化器状态 + 梯度） |
| | Agent/工具调用 | 需支持 function calling 的模型 + 规划能力 |
| **延迟要求** | 实时（<500ms） | 需多 GPU 张量并行 + 高带宽 GPU |
| | 交互式（<2s） | 单/双 GPU 配置即可 |
| | 批量处理（分钟级） | 可使用 CPU Offloading |
| **吞吐量** | 单用户 | 无需考虑批处理，关注 TTFT（首 Token 延迟） |
| | 10–50 并发 | 需 continuous batching + 请求队列 |
| | 100+ 并发 | 需专用推理服务器 + 负载均衡 |
| **数据隐私** | 完全离线 | 不可连接外网，需纯本地部署 |
| | 混合云 | 敏感数据本地，通用查询走云端 API |
| **预算** | 1–3 万 RMB | 7B–14B 模型 + 单消费级 GPU |
| | 5–20 万 RMB | 32B–72B 模型 + 多卡/工作站 GPU |
| | 50 万+ RMB | 百 B 以上 MoE 模型 + 数据中心 GPU |

#### 1.2 关键性能指标（KPI）

| 指标 | 定义 | 典型目标 |
|------|------|---------|
| **TTFT** (Time To First Token) | 请求发出到第一个 Token 生成的时间 | < 200ms（实时场景） |
| **TPOT** (Time Per Output Token) | 每个输出 Token 的生成时间 | < 30ms（>33 token/s） |
| **Throughput** | 每秒可处理的总 Token 数 | > 1000 tokens/s（多用户） |
| **QPS** | 每秒可处理的请求数 | 取决于并发架构 |
| **Max Context Length** | 最大支持的上下文长度 | 4K–128K（视模型而定） |

#### 3.7 硬盘/存储资源需求

大模型私有化部署中，存储系统的规划直接影响模型加载速度、推理服务可用性和运维效率。以下从容量估算、性能选型、分层架构到具体配置方案进行系统性阐述。

##### 3.7.1 存储需求构成分析

大模型部署的存储需求由多个组件构成，各自的容量占比和性能要求不同：

| 存储类别 | 具体内容 | 读写特征 | IOPS 敏感度 | 容量占比 |
|---------|---------|---------|------------|---------|
| **模型权重文件** | 原始模型、量化模型、多版本并存 | 读多写少，大块顺序读取 | 低 | 40%–60% |
| **推理框架与环境** | Docker 镜像、Python 虚拟环境、CUDA 库 | 读多写少，相对固定 | 低 | 5%–10% |
| **向量数据库** (RAG 场景) | Embedding 向量索引、文档分块元数据 | 随机小块读取为主 | 极高 | 10%–30% |
| **用户数据与日志** | 对话记录、审计日志、监控时序数据 | 持续追加写入 | 中 | 5%–15% |
| **系统与缓存** | 操作系统、Swap 分区、临时文件 | 混合读写 | 中 | 5%–10% |
| **备份与快照** | 模型备份、配置快照、灾难恢复副本 | 批量写入，极少读取 | 低 | 20%–50% (额外) |

##### 3.7.2 存储容量估算公式

```
总存储需求(GB) = 模型存储 + 系统环境 + 向量数据库 + 日志数据 + 备份冗余 + 预留空间

逐项估算:

1. 模型存储(GB) = Σ(每个模型参数量(B) × 每参数字节数 × 模型版本数 × 格式份数)
   
   例如:
   - Qwen2.5-72B 保留 FP16 + INT4 两个格式 + 2 个版本:
     = (72×2 + 72×0.5) × 2 = (144 + 36) × 2 = 360 GB
   - DeepSeek-V3 保留 FP8 + INT4 + 1 旧版本:
     = (671×1 + 671×0.5) × 2 = (671 + 336) × 2 ≈ 2,014 GB ≈ 2 TB

2. 系统环境(GB) ≈ 100–200 GB
   (Ubuntu Server + Docker 镜像 + Python 环境 + CUDA Toolkit)

3. 向量数据库(GB) ≈ 原始文档总量(GB) × 1.5–2.0
   (Embedding 索引膨胀系数，含 metadata 和索引结构)

4. 日志数据(GB) ≈ 日均日志量(GB) × 保留天数
   日均日志量参考: 单用户约 10–50 MB/天, 100 并发约 1–5 GB/天

5. 备份空间(GB) ≈ (模型存储 + 向量数据库) × 备份份数

6. 预留空间: 总量 × 20%–30% (应对突发增长)
```

**典型场景存储估算对照表：**

| 部署场景 | 模型文件 | 系统环境 | 向量数据库 | 日志 (30天) | 备份 (×2) | 预留 (25%) | **合计建议** |
|---------|---------|---------|-----------|------------|----------|-----------|------------|
| 个人开发者 (Qwen2.5-14B, 2版本) | ~20 GB | 100 GB | 50 GB (可选) | 5 GB | 40 GB | ~55 GB | **≥ 512 GB** |
| 小团队 (Qwen2.5-72B, 2格式 + Embedding) | ~180 GB | 150 GB | 200 GB | 30 GB | 360 GB | ~230 GB | **≥ 1 TB** |
| 中型企业 (多模型 + RAG + Agent) | ~500 GB | 200 GB | 500 GB | 100 GB | 1 TB | ~575 GB | **≥ 3 TB** |
| 大型企业 (DeepSeek-V3 + 多模型矩阵) | ~1.5 TB | 300 GB | 1 TB | 300 GB | 3 TB | ~1.5 TB | **≥ 8 TB** |
| 数据中心 (全部模型 + 高并发 + 长存储) | ~3 TB+ | 500 GB | 3 TB+ | 1 TB | 6 TB | ~3.4 TB | **≥ 15 TB** |

##### 3.7.3 存储性能要求详解

不同数据类型对存储的 IOPS、吞吐量和延迟有截然不同的要求：

| 数据类型 | 典型读写模式 | 块大小 | 顺序读吞吐需求 | 随机读 IOPS 需求 | 延迟要求 |
|---------|------------|--------|--------------|----------------|---------|
| **模型加载** (冷启动) | 顺序大块读取 | 128 KB–1 MB | ≥ 2–3 GB/s | 不敏感 | < 100ms 即可, 越低启动越快 |
| **模型加载** ( /dev/shm 预热) | 顺序读取 → 内存 | 1 MB | ≥ 5 GB/s | 不敏感 | — |
| **Embedding 向量索引** | 随机小块读取 | 4 KB–16 KB | 不敏感 | ≥ 10,000 IOPS | < 1ms (P99) |
| **推理日志写入** | 顺序追加写入 | 4 KB–64 KB | ≥ 50 MB/s (高并发) | 不敏感 | 无硬性要求 |
| **KV Cache 卸载到磁盘** | 随机读写混合 | 64 KB–256 KB | ≥ 1 GB/s | ≥ 5,000 IOPS | < 10ms |
| **模型文件下载** | 大块顺序写入 | 1 MB+ | ≥ 500 MB/s | 不敏感 | 无硬性要求 |
| **系统 Swap** (紧急) | 随机读写 | 4 KB (page) | 不敏感 | ≥ 20,000 IOPS | < 1ms |

##### 3.7.4 存储介质选型对比

| 介质类型 | 容量范围 (单盘) | 顺序读 (MB/s) | 顺序写 (MB/s) | 随机读 IOPS (4K) | 随机写 IOPS (4K) | 寿命 (DWPD) | 参考价格 (RMB/TB) | 适用场景 |
|---------|---------------|-------------|-------------|-----------------|-----------------|------------|------------------|---------|
| **HDD** (7200 RPM) | 1–22 TB | ~250 | ~250 | ~100 | ~100 | — | 200–400 | 冷备份、日志归档 |
| **SATA SSD** (消费级) | 256 GB–8 TB | ~550 | ~520 | ~95K | ~85K | 0.1–0.3 | 400–700 | 系统盘、日志盘 |
| **SATA SSD** (企业级) | 480 GB–8 TB | ~550 | ~520 | ~98K | ~90K | 1–3 | 800–1,500 | 温数据存储 |
| **NVMe PCIe 3.0** | 256 GB–8 TB | ~3,500 | ~3,000 | ~500K | ~500K | 0.3–1 | 500–1,000 | 消费级模型加载 |
| **NVMe PCIe 4.0** | 512 GB–8 TB | ~7,000 | ~5,000 | ~1,000K | ~1,000K | 0.3–1 | 800–1,500 | **推荐主力存储** |
| **NVMe PCIe 5.0** | 1–4 TB | ~12,000 | ~10,000 | ~1,500K | ~1,500K | 0.3–1 | 1,500–3,000 | 极致模型加载速度 |
| **U.2/U.3 NVMe** (企业级) | 1–30 TB | ~7,000 | ~3,500 | ~1,000K | ~200K | 1–3 | 2,000–5,000 | 企业热数据 + 向量索引 |

**关键选型建议：**

```
模型加载速度对比 (以 Qwen2.5-72B FP16 ≈ 144 GB 为例):

HDD (250 MB/s):          144 GB / 0.25 GB/s ≈ 576 秒 ≈ 9.6 分钟  ❌ 不可接受
SATA SSD (550 MB/s):     144 GB / 0.55 GB/s ≈ 262 秒 ≈ 4.4 分钟  ⚠️ 偏慢
NVMe PCIe 3.0 (3 GB/s):  144 GB / 3.0 GB/s  ≈ 48 秒             ✅ 可接受
NVMe PCIe 4.0 (6 GB/s):  144 GB / 6.0 GB/s  ≈ 24 秒             ✅ 推荐
NVMe PCIe 5.0 (10 GB/s): 144 GB / 10 GB/s   ≈ 14 秒             ✅ 最优

结论: 模型存储盘强烈建议使用 NVMe SSD (PCIe 4.0 或以上)
```

##### 3.7.6 RAID 配置建议

| RAID 级别 | 最少盘数 | 可用容量 (N 盘, 单盘 C) | 读性能 | 写性能 | 容错能力 | 适用场景 |
|-----------|---------|----------------------|--------|--------|---------|---------|
| **RAID 1** | 2 | C | 高 (可并发读) | 中 (单盘速度) | 1 盘故障 | 系统盘、热数据模型盘 |
| **RAID 5** | 3 | C × (N-1) | 高 (条带化读) | 中 (校验计算开销) | 1 盘故障 | 温数据模型存储、日志盘 |
| **RAID 6** | 4 | C × (N-2) | 高 | 低 (双重校验) | 2 盘故障 | 冷备份/归档盘 |
| **RAID 10** | 4 (偶数) | C × N/2 | 极高 (条带化+镜像) | 高 | 每对至少存活 1 盘 | 高并发向量索引、生产热数据 |
| **RAID 0** | 2 | C × N | 极高 | 极高 | 0 (无容错) | 仅临时缓存/测试 (不推荐生产) |

**RAID 配置实战建议：**

```
不推荐的做法:
  ✗ 所有数据放在单个大容量 HDD 上 → 加载缓慢，无容错
  ✗ 仅使用 RAID 0 存放模型 → 一块盘故障导致全部不可用
  ✗ 将日志和模型放在同一块盘 → 日志写满导致模型无法加载

推荐的做法:
  ✓ 系统盘 + 热模型用 RAID 1 NVMe → 安全 + 高速
  ✓ 多模型/历史版本用 RAID 5 → 容量与安全平衡
  ✓ 备份用 RAID 6 大容量 HDD → 最高容错，成本最低
  ✓ 向量索引用 RAID 10 → 随机读性能最大化
  ✓ 日志独立分区/磁盘 → 避免日志爆盘影响模型服务
```

```
  1. 模型临时/缓存文件 → 部署成功后立即清理
  2. Docker 旧镜像 → docker image prune -a (保留最近 2 个 tag)
  3. Python 缓存 → find /data -type d -name "__pycache__" -exec rm -rf {} +
  4. 推理日志 → logrotate 按天轮转，保留 30 天
  5. 审计日志 → 按月归档，保留 1 年以上 (合规)
```

##### 3.7.9 存储性能对推理各阶段的影响

| 推理阶段 | 存储相关操作 | 存储瓶颈后果 | 缓解措施 |
|---------|------------|------------|---------|
| **服务启动** | 模型从磁盘加载到显存 | 启动延迟 30s–10min+ | NVMe SSD + 预加载脚本 |
| **模型热切换** | 新模型加载，旧模型卸载 | 切换窗口数分钟，服务中断 | 双实例 Blue-Green + NVMe |
| **首次 Token (TTFT)** | 通常不涉及磁盘 (权重已在显存) | 罕见 | — |
| **RAG 检索增强** | Embedding 检索 → 向量索引读取 | TTFT 增加 50–500ms+ | NVMe RAID10 + 热索引内存缓存 |
| **长上下文推理** | KV Cache 溢出 → 卸载到磁盘 | tokens/s 下降 30%–80% | 充足显存优先；必须时 NVMe RAID0 |
| **日志记录** | 每次请求写入日志 | 高并发下 IO 阻塞 | 异步日志队列 + 批量刷盘 + 独立日志盘 |
| **模型下载** | 网络 → 磁盘顺序写入 | 下载速度受限于磁盘写速度 | NVMe 写入可匹配 10GbE 网络带宽 |

#### 5.4 Nginx 反向代理与 TLS 配置

```nginx
# /etc/nginx/sites-available/llm-api
upstream vllm_backend {
    server 127.0.0.1:8000 max_fails=3 fail_timeout=30s;
    # 多实例时添加更多 backend
    # server 127.0.0.1:8001 max_fails=3 fail_timeout=30s;
    keepalive 32;
}

# 限流区域配置
limit_req_zone $binary_remote_addr zone=api_rate:10m rate=10r/s;
limit_conn_zone $binary_remote_addr zone=conn_limit:10m;

server {
    listen 443 ssl http2;
    server_name llm-api.your-domain.com;

    # TLS 证书配置
    ssl_certificate     /etc/nginx/ssl/fullchain.pem;
    ssl_certificate_key /etc/nginx/ssl/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384;
    ssl_prefer_server_ciphers on;
    ssl_session_cache shared:SSL:10m;

    # 安全头
    add_header X-Content-Type-Options nosniff;
    add_header X-Frame-Options DENY;
    add_header Strict-Transport-Security "max-age=63072000" always;

    location /v1/ {
        # 限流
        limit_req zone=api_rate burst=20 nodelay;
        limit_conn conn_limit 10;

        # 代理到 vLLM
        proxy_pass http://vllm_backend/v1/;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 超时配置（SSE 流式响应需长超时）
        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
        proxy_buffering off;  # 关闭缓冲以支持 SSE 流式输出

        # 请求体限制
        client_max_body_size 10m;
    }

    # 健康检查端点
    location /health {
        proxy_pass http://vllm_backend/health;
        access_log off;
    }
}

# HTTP → HTTPS 重定向
server {
    listen 80;
    server_name llm-api.your-domain.com;
    return 301 https://$host$request_uri;
}
```

### 4.3 总拥有成本（TCO）计算模型

```
TCO = 硬件购置成本 + 运营成本 + 间接成本

详细展开:

TCO_yearly = H + (P × E × T) + M + N + C + D

其中:
  H (Hardware)      = 服务器/GPU 购置成本 / 折旧年限
  P (Power)         = 服务器总功耗 (kW)
  E (Electricity)   = 电价 (RMB/kWh)
  T (Time)          = 年运行小时数
  M (Maintenance)   = 运维人力成本 (RMB/年)
  N (Network)       = 带宽成本 (RMB/年)
  C (Cooling)       = 冷却成本 (RMB/年)
  D (Depreciation)  = 硬件折旧 (通常按 3–5 年直线折旧)
```

#### 4.3.2 盈亏平衡分析

```
自建 vs 云租赁盈亏平衡点 (以 4×A100 80GB 为例):

自建成本: ¥500,000 (一次性)
云租赁成本: ¥4,320/月/卡 × 4 卡 × 12 月 = ¥207,360/年

n = 500,000 / 207,360 ≈ 2.4 年

结论: 如果预计使用 GPU 超过 2.5 年，自建更经济；
      短期项目 (< 2.5 年) 或需要弹性伸缩，选择云租赁。

自建 vs API 订阅盈亏平衡点 (以 DeepSeek API 为例):

DeepSeek API 定价: ¥1/百万输入 tokens + ¥2/百万输出 tokens
假设日处理 500 万 tokens (输入:输出 = 3:1):
  日 API 费用 = 3.75×1 + 1.25×2 = ¥6.25/日 → ¥2,281/年

单张 4090 自建 (可用 7B 模型):
  年 TCO ≈ ¥9,341

n = 9,341 / 2,281 ≈ 4.1 年 → API 订阅明显更省

但如果吞吐量增长到日处理 5000 万 tokens:
  日 API 费用 = ¥62.5/日 → ¥22,812/年
  n = 9,341 / 22,812 ≈ 0.41 年 → 自建立即划算

结论: 低吞吐场景 API 划算；高吞吐场景自建划算。
      API 订阅适合: 日 token 量 < 1000 万
      自建适合: 日 token 量 > 3000 万 或 数据隐私要求高
```

### 6.4 API 认证中间件示例

```python
# 基于 FastAPI 中间件的 API Key 认证（嵌入 vLLM 使用）
import hashlib
import time
from fastapi import HTTPException, Request

class APIKeyAuth:
    def __init__(self, api_keys: dict):
        # api_keys: {"key_hash": {"name": "user", "rate_limit": 10, "expires": timestamp}}
        self.api_keys = api_keys

    async def __call__(self, request: Request):
        api_key = request.headers.get("Authorization", "").replace("Bearer ", "")

        if not api_key:
            raise HTTPException(status_code=401, detail="Missing API key")

        key_hash = hashlib.sha256(api_key.encode()).hexdigest()
        key_info = self.api_keys.get(key_hash)

        if not key_info:
            raise HTTPException(status_code=403, detail="Invalid API key")

        if key_info.get("expires", float("inf")) < time.time():
            raise HTTPException(status_code=403, detail="API key expired")

        request.state.user = key_info["name"]
        request.state.rate_limit = key_info.get("rate_limit", 10)
```

**Blue-Green 部署脚本示例：**

```bash
#!/bin/bash
# blue-green-deploy.sh

MODEL_V1="/data/models/qwen-72b-v1/"
MODEL_V2="/data/models/qwen-72b-v2/"
GREEN_PORT=8001

echo "=== Step 1: 启动 Green 实例 (新模型) ==="

  --gpus '"device=0,1,2,3"' \
  --name vllm-green \
  -p $GREEN_PORT:8000 \
  -v $MODEL_V2:/models/ \
  vllm/vllm-openai:latest \
  --model /models/ \
  --tensor-parallel-size 4

echo "=== Step 2: 等待 Green 实例就绪 ==="
for i in $(seq 1 60); do
  if curl -s http://localhost:$GREEN_PORT/health > /dev/null 2>&1; then
    echo "Green instance is healthy!"
    break
  fi
  echo "Waiting... ($i/60)"
  sleep 5
done

echo "=== Step 3: 执行预热请求 ==="
curl -s http://localhost:$GREEN_PORT/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"qwen","messages":[{"role":"user","content":"Hello"}],"max_tokens":10}' \
  > /dev/null

echo "=== Step 4: 切换 Nginx Upstream ==="
sudo sed -i 's/server 127.0.0.1:8000/server 127.0.0.1:8001/' /etc/nginx/sites-enabled/llm-api
sudo nginx -s reload

echo "=== Step 5: 等待排空 Blue 实例 ==="
sleep 30

echo "=== Step 6: 停止 Blue 实例 ==="
docker stop vllm-blue
docker rm vllm-blue

echo "=== 部署完成! 新模型已上线 ==="
```

### 7.5 常见问题速查表

| 问题现象 | 可能原因 | 排查命令 | 解决方案 |
|---------|---------|---------|---------|
| `CUDA out of memory` | 模型/批次/KV Cache 超出显存 | `nvidia-smi` 查看显存 | 量化、减小 batch、TP 切分 |
| 推理速度 < 10 tokens/s | 未使用 Flash Attention | `pip list \| grep flash` | 安装 flash-attn |
| GPU 利用率 < 50% | CPU 瓶颈 / batch 过小 | `htop` + `nvidia-smi` | 减小 CPU 计算、增大 batch |
| 首 token 延迟 > 2s | Prompt 过长 / 模型加载慢 | 查看 Prefill 耗时 | Chunked Prefill, Prefix Cache |
| 多用户时速度骤降 | 未启用 Continuous Batching | 查看框架配置 | 换用 vLLM/SGLang |
| 随机输出乱码 | 量化模型损坏 / 精度不足 | 重新下载 hash 校验 | 使用 Q4_K_M 以上精度 |
| Docker GPU 不可见 | nvidia-container-toolkit 未装 | `docker run --gpus all nvidia/cuda:12.4.0-base-ubuntu22.04 nvidia-smi` | 重装 toolkit |
| 模型下载中断 | HuggingFace 网络不稳定 | 查看下载进度 | 设置 HF 镜像 `HF_ENDPOINT=https://hf-mirror.com` |
