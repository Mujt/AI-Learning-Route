# 第 5 章 上下文工程 Context Engineering

## 学习目标

- 理解上下文工程的概念与重要性
- 掌握上下文的设计、检索、存储更新与管理策略
- 掌握长上下文场景的成本与性能平衡方法
- 构建高质量上下文管理机制

---

## 5.1 上下文工程概述

### 5.1.1 什么是上下文工程

**上下文工程（Context Engineering）** 是围绕"如何为 LLM 提供高质量、低成本、可扩展的上下文"的系统工程。它不是某个单一技巧，而是**上下文的全生命周期管理**：

```
上下文设计 → 上下文检索 → 上下文存储与更新 → 上下文管理与优化
```

### 5.1.2 为什么上下文工程至关重要

- **模型能力上限 = 上下文质量**：同样一个模型，喂什么上下文决定输出质量。
- **Token 成本**：上下文直接决定 API 账单（长上下文成本随长度线性增长）。
- **长上下文 ≠ 高智商**：研究表明模型存在"上下文迷失"（Lost in the Middle），对超长上下文的中间部分利用率低。
- **Agent 场景**：Agent 的多轮工具调用会产生海量中间上下文，管理不当直接崩坏。

### 5.1.3 上下文工程的三个基本问题

1. **给什么**：什么信息值得进上下文（相关性、重要性、时效性）。
2. **给多少**：上下文预算如何分配（核心 vs 辅助）。
3. **怎么给**：格式、顺序、结构如何最优呈现。

## 5.2 上下文的设计

### 5.2.1 上下文的结构化设计

| 设计维度 | 原则 | 示例 |
|----------|------|------|
| 分层 | 关键信息前置，重要内容放首尾 | 指令 → 核心资料 → 背景 |
| 分段 | 用分隔符/标签明确分区 | `<system>`、`<context>`、`<tools>` |
| 标注 | 每个上下文片段带来源与权重 | [文档1-第2节] [优先级:高] |
| 压缩 | 先摘要再入上下文 | 长文档先"摘要+关键段落" |

### 5.2.2 Prompt 与上下文的分工

```
【指令层】系统提示词：角色、任务、规则（相对固定）
【知识层】检索上下文：与本次任务相关的事实
【示例层】Few-shot 示例：输出格式示范
【动态层】实时信息：工具结果、用户输入、状态
```

**设计原则**：指令层保持精简稳定；知识层动态注入；示例层按需增减。

## 5.3 上下文的检索

### 5.3.1 检索式上下文（RAG 的上下文视角）

RAG 的本质就是**上下文工程中的"按需检索注入"**：

- 检索 Top-K 片段 → 组装上下文 → 送入模型。
- 关键参数：K 值（数量）、切分大小（粒度）、相关性阈值（质量门禁）。

### 5.3.2 上下文选择的四大原则

| 原则 | 说明 |
|------|------|
| 相关性优先 | 只保留与问题直接相关的片段 |
| 去重去噪 | 合并相似片段，剔除冗余 |
| 时效性过滤 | 过期信息标记或剔除 |
| 权限过滤 | 按用户权限裁剪上下文 |

### 5.3.3 面向长文档的上下文组装

```
长文档（100 页）处理：
① 全文 → 章节摘要索引
② 问题 → 检索命中相关章节
③ 组装：章节摘要 + 命中的关键段落（而非全文）
④ 若需全局理解 → 多个章节摘要聚合
```

## 5.4 上下文的存储与更新

### 5.4.1 多轮对话的上下文管理

| 策略 | 原理 | 适用 |
|------|------|------|
| 滑动窗口 | 只保留最近 N 轮 | 简单场景 |
| 摘要压缩 | 旧消息定期压缩成摘要 | 长会话 |
| 混合策略 | 最近 N 轮原文 + 更早的摘要 | 生产常用 |
| 向量召回 | 历史消息向量化按需召回 | 个性化助手 |

### 5.4.2 记忆体系（长期上下文）

```
短期记忆（会话级）: 当前会话消息（Redis/SQLite 持久化）
长期记忆（用户级）: 用户画像、偏好、知识（向量库）
情景记忆（任务级）: 当前任务的目标、状态、结果（State）
```

**更新机制**：记忆写回需"事后总结"（如每 5 轮对话总结一次用户偏好），避免记忆污染。

## 5.5 上下文的管理与优化

### 5.5.1 上下文预算管理

```
总预算 = 模型上下文窗口 × 安全系数（如 80%）
分配建议：
  系统指令   10%
  检索上下文 40%
  对话历史   30%
  输出预留   20%（模型输出也占窗口）
```

### 5.5.2 缓解"上下文迷失"（Lost in the Middle）

- 现象：模型对长上下文**中间部分**的注意力最弱。
- 对策：
  1. 关键信息放**开头**（系统指令/核心资料）或**结尾**（最新问题）。
  2. 控制单次上下文长度（优先精而非多）。
  3. 用分隔符和格式强化关键信息可读性。

### 5.5.3 上下文压缩技术

| 技术 | 做法 | 效果 |
|------|------|------|
| LLM 摘要 | 定期压缩历史消息 | 保留语义，大幅降本 |
| 结构化提取 | 只提取关键字段/结论 | 精准降噪 |
| 关键句抽取 | 抽取与问题相关的句子 | 压缩比高 |
| 分层摘要 | 摘要树（按章节层级） | 长文档场景 |

### 5.5.4 上下文质量监控

- **指标**：上下文相关率、冗余率、Token 成本/次会话。
- **工具**：LangSmith/Langfuse 追踪每次调用送入的上下文，分析"上下文质量 vs 回答质量"的相关性。
- **A/B**：同一问题在不同上下文策略下的输出质量对比。

## 5.6 实战：电商客服的上下文工程

```
【会话开始】
系统指令（精简固定）：角色、规则、可用工具
用户画像（向量召回）：VIP 用户、历史投诉记录
【每轮】
  - 最新用户消息（高优先级，放最后）
  - 相关订单/商品检索上下文（放中部）
  - 历史对话：最近 5 轮原文 + 之前摘要
【工具调用】
  - 工具结果 → 压缩为"关键结论"再入上下文
【会话结束】
  - 总结用户偏好 → 写回长期记忆
```

## 常见问题（FAQ）

**Q1：把模型上下文窗口买大点（如 200K）是不是一劳永逸？**
A：不是。长窗口不等于高质量：①成本线性上涨；②存在"上下文迷失"；③检索仍是长文档的首选方案。大窗口应该"用得起"，而不是"全塞进去"。

**Q2：上下文工程和 RAG 是什么关系？**
A：RAG 是上下文工程的**核心实现手段之一**（检索式上下文）。上下文工程是更宏观的框架，涵盖记忆、压缩、预算等 RAG 之外的领域。

**Q3：记忆写进上下文会不会泄露隐私？**
A：会。需做三层防护：①按权限裁剪；②敏感字段脱敏；③记忆内容审计与删除机制（合规要求）。
