## 7.1 部署环境规划

### 7.1.1 显存需求计算

**推理显存 = 模型权重 + KV Cache + 激活/计算缓冲**

```
模型权重：
  FP16/BF16: 参数量 × 2 字节
  INT8:      参数量 × 1 字节
  INT4:      参数量 × 0.5 字节

KV Cache（每序列）：
  ≈ 2 × 层数 × 头数 × 头维度 × 序列长度 × 每字节
  近似：2 × num_layers × hidden_size × seq_len × dtype_size
  例：7B 模型（32层, hidden 3584, 8bit, 4K 上下文）≈ 4.4GB/并发序列
```

### 7.1.2 部署算力规划实战表

| 模型 | 精度 | 权重显存 | 建议显卡 | 并发建议 |
|------|------|----------|----------|----------|
| 1.5B | INT4 | ~1GB | 8G 消费卡 | 数十并发 |
| 7B | INT4 | ~3.5GB | 16-24G | 10-30 并发 |
| 7B | FP16 | ~14GB | 24G | 5-15 并发 |
| 14B | INT4 | ~7GB | 24G | 10-20 并发 |
| 32B | INT4 | ~16GB | 40G 或双 24G | 5-15 并发 |
| 72B | INT4 | ~36GB | 2×80G | 5-20 并发 |
| 72B | FP16 | ~144GB | 4×80G | 高并发 |

> 经验：**先量化，再算并发**；预留 20-30% 显存余量给调度与波动。

### 7.1.3 其他环境要素

- **CPU/内存**：模型加载与调度需要足够内存（建议 ≥ 权重体积 × 2）。
- **网络**：多卡推理需 NVLink/PCIe 高速互联；集群需 25G/100G 内网。
- **磁盘**：模型文件存储 + 缓存（NVMe SSD）。
- **软件栈**：CUDA + cuDNN + PyTorch + 推理框架（vLLM/SGLang）。

## 7.2 模型部署架构

### 7.2.1 部署形态选型

```
┌ 单机单卡：小模型（≤7B INT4）/ 低并发 / 开发环境
├ 单机多卡：大模型（并行）或 小模型（多实例负载均衡）
├ 多机集群：超大模型（72B+）/ 高并发生产
└ 边缘部署：手机/PC（1-3B 量化，llama.cpp/ONNX）
```

### 7.2.2 生产部署参考架构

```

│ 应用层：Web / 小程序 / Agent 平台        │
├─────────────────────────────────────────┤

```

### 7.2.3 多模型管理（模型网关）

企业通常部署多个模型（不同尺寸/任务），用**模型网关**统一管理：

```
Model Router / LiteLLM / OneAPI
  ├── 按模型路由：chat-small → 7B，chat-large → 72B
  ├── 按任务路由：代码 → Code 模型，翻译 → 翻译模型
  ├── 负载均衡 + 故障转移
  └── 统一计费与 Key 管理
```

## 7.3 多卡并行与推理优化

### 7.3.1 三种并行模式

```
张量并行（TP）：权重矩阵按行/列切分到多卡，单层计算多卡协作
                → 适合单卡放不下的模型（14B+ 常见）
流水线并行（PP）：按层切分，层组流水执行（如 96 层分 4 段各 24 层）
                → 适合超大模型
数据并行（DP）：完整模型复制多卡，不同请求打到不同卡
                → 提升吞吐（最简单）
```

| 并行 | 通信量 | 显存节省 | 适用 |
|------|--------|----------|------|
| TP | 高（每层同步） | 大 | 中等模型单机多卡 |
| PP | 低（仅边界） | 大 | 超大模型集群 |
| DP | 低 | 无（复制） | 多实例吞吐 |

### 7.3.2 主流并行组合

- **Megatron-LM**：TP + PP + DP 深度融合（大规模训练/推理）。
- **vLLM**：内置 TP（`--tensor-parallel-size`），一行配置。
- **DeepSpeed**：Zero-Offload、ZeRO 推理优化。

```bash
# vLLM 多卡张量并行部署
vllm serve Qwen/Qwen2.5-72B-Instruct \
    --tensor-parallel-size 4 \
    --gpu-memory-utilization 0.9 \
    --max-model-len 8192 \
    --dtype bfloat16
```

### 7.3.3 KV Cache 与推理加速

| 技术 | 原理 | 效果 |
|------|------|------|
| **KV Cache** | 缓存历史 K/V，避免重复计算 | 速度提升 10-100×（已内置于主流框架） |
| **GQA/MQA** | 多查询共享 KV | 减少 KV 显存 70-90% |
| **KV 量化** | KV Cache 用 INT8/FP8 存储 | 显存减半，轻微精度损失 |
| **FlashAttention** | IO 优化的注意力计算 | 速度与显存双优 |
| **投机采样（Speculative Decoding）** | 小模型草稿 + 大模型验证 | 吞吐提升 2-3× |
| **Prefix Caching** | 相同系统提示词缓存 | 多轮/多用户场景大提速 |
| **Continuous Batching** | 动态批量调度 | 吞吐提升数倍（vLLM 核心） |

### 7.3.4 部署优化决策树

```
吞吐瓶颈？ → vLLM 连续批处理 + Prefix Cache + 投机采样
显存瓶颈？ → 量化 + GQA/KV量化 + gpu-memory-utilization 调优
延迟瓶颈？ → 小模型 + 投机采样 + 流式输出（SSE）+ 首Token优化
模型太大？ → TP/PP 并行 + 量化 + 卸载策略
```

## 常见问题（FAQ）

**Q1：gpu-memory-utilization 设多少合适？**
A：一般 0.85-0.95。过高会触发 OOM（无余量给碎片与调度），过低浪费显存。从 0.9 开始实测调整。

**Q2：TP 和 PP 先选哪个？**
A：单机内优先 TP（通信快）；跨机或超大模型才用 PP。多数 14B-72B 场景，单机 2-4 卡 TP 即可。

**Q3：为什么我的推理服务并发一高就 OOM？**
A：最常见原因是 KV Cache 占用超预估：每增加一个并发序列就多占一份 KV 显存。降低 max-model-len、开 KV 量化、或缩减并发上限。
