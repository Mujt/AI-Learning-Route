## 8.1 vLLM 推理服务

### 8.1.1 vLLM 核心原理

vLLM 是业界最主流的 LLM 推理框架，核心创新 **PagedAttention（分页注意力）**：

- **传统 KV Cache**：为每条序列预分配连续显存（按最大长度），浪费 60-80%。
- **PagedAttention**：KV Cache 按**固定大小块**（Page）管理，类似操作系统的分页——只分配实际使用的块，显存利用率提升至 90%+。

加上 **Continuous Batching（连续批处理）**——动态把新请求插入正在生成的批次，吞吐较传统方案提升 2-4 倍（官方数据最高 24 倍）。

### 8.1.2 启动 OpenAI 兼容服务

```bash
# 部署 Qwen2.5-7B
vllm serve Qwen/Qwen2.5-7B-Instruct \
    --host 0.0.0.0 --port 8000 \
    --dtype bfloat16 \
    --max-model-len 8192 \
    --gpu-memory-utilization 0.9 \
    --served-model-name qwen2.5-7b \
    --enable-prefix-caching
```

### 8.1.3 客户端调用（OpenAI 兼容）

```python
from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")
stream = client.chat.completions.create(
    model="qwen2.5-7b",
    messages=[{"role": "user", "content": "写一首关于秋天的诗"}],
    temperature=0.7, max_tokens=512,
    stream=True,                          # 流式输出
)
for chunk in stream:
    if chunk.choices[0].delta.content:
        print(chunk.choices[0].delta.content, end="")
```

### 8.1.4 vLLM 关键参数

| 参数 | 作用 | 建议 |
|------|------|------|
| `--gpu-memory-utilization` | GPU 显存使用上限 | 0.85-0.95 |
| `--max-model-len` | 最大上下文长度 | 按业务需求 |
| `--enable-prefix-caching` | 前缀缓存 | 固定系统提示词时开启 |
| `--tensor-parallel-size` | 张量并行卡数 | 大模型按显存设 |
| `--quantization` | 量化格式（awq/gptq） | 匹配模型格式 |
| `--served-model-name` | 对外模型名 | 与网关一致 |
| `--max-num-seqs` | 最大并发序列 | 与显存匹配 |

## 8.2 容器化部署

### 8.2.1 Docker 部署 vLLM

```dockerfile
# Dockerfile
FROM vllm/vllm-openai:latest
COPY ./models /models
# 模型也可挂载卷
```

```yaml
# docker-compose.yml（单实例）
services:
  llm:
    image: vllm/vllm-openai:latest
    command: >
      --model /models/Qwen2.5-7B-Instruct
      --served-model-name qwen2.5-7b
      --port 8000
      --gpu-memory-utilization 0.9
    ports: ["8000:8000"]
    volumes: ["./models:/models"]
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu]
    restart: always
```

```bash
docker compose up -d
docker logs -f llm      # 查看启动日志
curl http://localhost:8000/v1/models
```

### 8.2.2 Kubernetes 生产部署

- **GPU 调度**：NVIDIA Device Plugin 分配 GPU。
- **弹性伸缩**：HPA 按 QPS/队列长度自动扩缩容。
- **滚动升级**：模型灰度切换（先切 10% 流量）。
- **故障自愈**：探针（liveness/readiness）+ 重启策略。

```yaml
# K8s 部署片段
apiVersion: apps/v1
kind: Deployment
metadata: { name: llm-service }
spec:
  replicas: 2
  template:
    spec:
      containers:
      - name: vllm
        image: vllm/vllm-openai:latest
        command: ["vllm", "serve", "/models/qwen2.5-7b", "--port", "8000"]
        resources:
          limits:
            nvidia.com/gpu: "1"
        ports: [{containerPort: 8000}]
```

## 8.3 性能监控

### 8.3.1 监控指标体系

| 类别 | 指标 | 工具 |
|------|------|------|
| 资源 | GPU 利用率、显存、温度、功耗 | nvidia-smi / DCGM + Prometheus |
| 服务 | QPS、吞吐（tokens/s）、成功率、错误率 | vLLM 指标 + Prometheus |
| 延迟 | TTFT（首 Token）、TPOT（每 Token）、总时延 | 追踪 + 统计 |
| 队列 | 请求排队数、排队等待时间 | 自研指标 |
| 业务 | 会话数、Token 消耗、成本 | 应用层埋点 |

## 8.4 性能压测与调优

### 8.4.1 Locust 压测

```python
# locustfile.py
from locust import HttpUser, task, between

class LLMUser(HttpUser):
    wait_time = between(0.5, 2)

    @task
    def chat(self):
        self.client.post("/v1/chat/completions", json={
            "model": "qwen2.5-7b",
            "messages": [{"role": "user",
                          "content": "请介绍一下大模型量化技术"}],
            "max_tokens": 200,
        })
```

```bash
locust -f locustfile.py --host http://localhost:8000 \
       --users 50 --spawn-rate 10 --run-time 5m
```

### 8.4.2 压测结果解读

| 指标 | 含义 | 优化手段 |
|------|------|----------|
| QPS | 每秒请求数 | 连续批处理、前缀缓存、多实例 |
| TTFT | 首 Token 延迟 | 前缀缓存、降低排队、KV 预分配 |
| TPOT | 每 Token 生成延迟 | 投机采样、量化、模型并行 |
| 成功率 | <99.5% 需排查 | 超时、OOM、限流配置 |
| GPU 利用率 | <60% 说明未榨干 | 增大并发、调 batch |

### 8.4.3 调优 Checklist

1. 开启 Continuous Batching（vLLM 默认）。
2. 开启 Prefix Caching（固定 prompt 场景）。
3. KV Cache 量化（显存紧张时）。
4. 量化模型（INT4 提速 + 省显存）。
5. 合适的 `--max-num-seqs`（与显存平衡）。
6. 预热 + 重试策略 + 超时配置。

## 8.5 安全与稳定性

### 8.5.1 服务安全

| 层次 | 措施 |
|------|------|
| 网络 | 内网隔离 / TLS / API Key 认证 |
| 应用 | 输入长度限制、内容安全过滤、Prompt 注入防护 |
| 资源 | 限流（Rate Limit）、配额管理、防滥用 |
| 数据 | 日志脱敏、会话数据加密存储 |

### 8.5.2 稳定性设计

- **高可用**：多副本 + 负载均衡 + 故障转移。
- **弹性**：K8s HPA 自动扩缩容。
- **降级**：主模型故障 → 切备用小模型（`--fallback`）。
- **限流熔断**：网关层限流 + 熔断器保护下游。
- **备份恢复**：模型文件、配置、数据库定期备份。
- **告警**：OOM 风险、QPS 异常、错误率上升、显存高位预警。

### 8.5.3 上线 CheckList

## 常见问题（FAQ）

**Q1：vLLM 和 Ollama 的区别？**
A：vLLM 面向生产高吞吐（连续批处理、PagedAttention、多卡并行）；Ollama 面向易用（一键安装、本地调试）。生产选 vLLM，个人/开发选 Ollama。

**Q2：TTFT 很高但 TPOT 正常，什么问题？**
A：通常是排队等待过长（并发超限）或前缀缓存未命中（每请求全量处理 system prompt）。增加实例、开前缀缓存、优化调度。

**Q3：GPU 利用率高但 QPS 上不去？**
A：可能瓶颈在单请求生成过长（max_tokens 过大）或 batch 未打满。压测时控制输出长度一致，检查 max-num-seqs 与调度配置。
