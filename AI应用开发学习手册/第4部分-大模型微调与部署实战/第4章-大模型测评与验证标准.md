## 4.1 大模型评估现状与评价体系

### 4.1.1 为什么评估难

1. **能力维度多**：语言、推理、代码、数学、多模态、安全……
2. **基准饱和**：公开榜单一度"刷分"成风，模型针对性过拟合。
3. **自动评估局限**：LLM-as-Judge 有偏差，人工评估成本高。
4. **场景差异**：通用榜第一 ≠ 领域场景好用。

### 4.1.2 评估体系分层

```
┌── 通用能力评估（基准测试）──┐
│  MMLU / C-Eval / SuperCLUE  │
├── 任务能力评估 ──────────────┤
│  代码 HumanEval / 数学 GSM8K │
│  推理 BBH / 中文 CMMLU       │
├── 场景评估（业务级）──────────┤
│  领域数据集 + 人工评分       │
├── 生产评估 ─────────────────┤
│  线上 A/B 测试 + 用户反馈    │
└─────────────────────────────┘
```

## 4.2 主流评测基准

### 4.2.1 综合能力基准

| 基准 | 内容 | 特点 |
|------|------|------|
| **MMLU** | 57 学科多选题 | 国际最通用的综合基准 |
| **C-Eval** | 中文 52 学科 | 中文综合能力代表 |
| **CMMLU** | 中文 67 学科 | 更偏中文与中国文化 |
| **SuperCLUE** | 中文综合（语言/推理/知识） | 国内榜单影响力大 |
| **HELM** | 斯坦福多场景综合 | 方法论严谨、多指标 |
| **Open LLM Leaderboard** | HF 综合榜 | 社区影响力大 |

### 4.2.2 专项能力基准

| 能力 | 基准 | 说明 |
|------|------|------|
| 代码 | HumanEval / MBPP | 代码生成正确率 |

| 中文知识 | CHiD / C3 | 中文阅读理解 |

## 4.3 大模型评估实践

### 4.3.1 自动化评估（Benchmark 跑分）

```bash
# 使用 lm-evaluation-harness（Hugging Face 官方评估工具）
pip install lm-evaluation-harness

lm_eval --model hf --model_args pretrained=Qwen/Qwen2.5-7B-Instruct \
        --tasks mmlu,c_eval,gsm8k \
        --batch_size auto --output_path ./results
```

**使用注意**：
- 版本锁定：不同 harness 版本跑分不可直接比较。
- Few-shot 设置：基准标准是 0-shot 还是 5-shot 需说明。
- 温度设置：评估通常 temperature=0（确定性）。

### 4.3.2 人工评估（Human Evaluation）

**维度评分表设计**：

| 维度 | 1-5 分标准 |
|------|-----------|
| 正确性 | 事实准确、无幻觉 |
| 相关性 | 切题、完整覆盖需求 |
| 可读性 | 流畅、结构清晰 |
| 风格一致性 | 符合目标风格 |
| 安全性 | 无不安全/偏见内容 |

**方法**：
- 成对比较（Pairwise）：A/B 盲测，标注者选更优。
- 单点评分（Rating）：逐条打分取均值。
- 注：需多人标注 + 一致性校验（Cohen's Kappa）。

### 4.3.3 LLM-as-Judge（模型评委）

```python
def judge(question, answer_a, answer_b):
    prompt = f"""请作为公正评委，比较两个回答：
问题：{question}
回答A：{answer_a}
回答B：{answer_b}
从正确性、相关性、完整性评估，输出 WINNER(A/B/TIE) 及理由。"""
    resp = judge_llm.invoke(prompt)
    return parse_winner(resp)
```

**注意事项**：
- 位置偏差：A/B 顺序互换多次取多数。
- 长度偏差：防止评委偏好长答案。
- 评委模型需强于被评模型（或用 GPT-4/Qwen-Max 级）。

## 4.4 微调模型的评估方法（核心流程）

### 4.4.1 微调评估五步法

```
① 基座模型基线跑分（微调前记录）
② 通用能力回归测试（MMLU/C-Eval，防遗忘）
③ 领域能力测试（自建领域测试集）
④ 场景人工评测（业务人员 30-50 条盲测）
⑤ 上线 A/B 测试（真实流量对比）
```

### 4.4.2 微调测试集设计

- **领域测试集**：300-1000 条，覆盖业务高频场景 + 边界场景（与训练数据隔离）。
- **回归测试集**：通用任务子集，验证是否灾难性遗忘。
- **对抗测试**：恶意 Prompt、敏感问题，验证安全性未退化。

### 4.4.3 微调评估实战表格

| 检查项 | 基座模型 | 微调模型 | 结论 |
|--------|----------|----------|------|
| C-Eval（通用） | 65.2 | 64.8 | 无明显遗忘 ✓ |
| 领域测试集（业务） | 52.1 | 78.3 | 大幅提升 ✓ |
| 指令遵循（IFEval） | 68.0 | 70.1 | 保持 ✓ |
| 安全测试 | 通过 | 通过 | ✓ |

### 4.4.4 常见评估陷阱

1. **数据泄漏**：测试集混入训练数据 → 分数虚高（务必隔离）。
2. **小样本噪声**：测试集 <100 条时分数波动大。
3. **过度调基准**：为刷分针对性优化 → 上线失效。
4. **忽略成本**：评估只看质量不看延迟/成本。

## 常见问题（FAQ）

**Q1：通用基准分数高就代表模型好用吗？**
A：不一定。通用基准测的是"平均能力"，业务场景更看重特定任务的可靠性。正确做法是"通用基准防退化 + 领域测试集验能力"。

**Q2：评估集应该建多大？**
A：领域验证集建议 300-1000 条（覆盖高频 + 边界）；回归测试集 100-200 条即可。太小波动大，太大成本高。

**Q3：微调后如何防止能力退化？**
A：三管齐下——①混入 10-30% 通用指令数据；②用较小的学习率与适量 epoch；③每次微调后跑回归测试，发现退化及时回滚。
