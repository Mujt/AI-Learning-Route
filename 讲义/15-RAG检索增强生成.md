## 四、核心知识点详解

### 4.1 为什么需要 RAG？

#### 4.1.1 大模型的知识从哪里来？

要理解 RAG，首先要明白一个大模型（如 ChatGPT、DeepSeek、Claude）"知道"什么、"不知道"什么。

大模型在训练阶段"阅读"了海量的互联网文本、书籍、论文、代码等数据。训练完成后，这些知识被"压缩"在模型的参数中。当用户提问时，模型根据参数中的知识来生成回答。

这个过程的本质问题是：

> **大模型的知识 = 训练数据中的知识，且截止到训练完成的那一天。**

这意味着 LLM 有一个天然的知识边界：

```
┌─────────────────────────────────────────────────────────┐
│              大模型的知识范围                              │
│                                                         │
│  ✅ LLM 知道：                                           │
│  · 训练数据中出现的公开知识（历史、科学、常识等）            │
│  · 截止到训练日期的信息（如 GPT-4 训练截止到 2023 年底）    │
│                                                         │
│  ❌ LLM 不知道：                                         │
│  · 你公司的内部文档、制度、流程                            │
│  · 训练日期之后发生的新事件（如 2026 年的新闻）             │
│  · 你的个人数据（日程、笔记、项目文件）                    │
│  · 专业的、小众的、未公开的领域知识                        │
│  · 特定行业的最新法规、标准                                │
│                                                         │
│  ⚠️ LLM 最大的危险：                                     │
│  当它"不知道"时，它不会沉默 —— 它可能会"自信地编造"！        │
│  这就是著名的 LLM 幻觉（Hallucination）问题。              │
└─────────────────────────────────────────────────────────┘
```

#### 4.1.2 一个真实的场景对比

让我们用一个具体的场景来感受 RAG 的价值：

**场景**：你是一家公司的员工，想了解公司最新的请假制度。公司的请假制度文档是一份内部 PDF，从未公开到互联网上。

**方案一：直接问 LLM（没有 RAG）**

```
用户：公司最新的请假流程是什么？

LLM（GPT/DeepSeek）：根据一般的公司管理实践，请假流程通常包括：
1. 向直属领导提交请假申请
2. 填写请假单
3. HR 部门审批
4. ...（开始泛泛而谈，或者编造一个看起来合理的流程）

问题：
- LLM 根本没见过你们公司的请假制度文档
- 它给出的回答是"通用常识"，不是"你们公司的真实规定"
- 如果它编造了某个步骤，你可能照做 → 误事！
- 最可怕的情况：它编造的内容"看起来完全正确"，你无法分辨真假
```

**方案二：使用 RAG（检索增强生成）**

```
用户：公司最新的请假流程是什么？

RAG 系统内部流程：
1. 从公司文档库中检索到"公司请假制度（2026年修订版）"
2. 提取相关段落："登录OA系统 → 选择请假类型 → 填写起止时间 →
    提交审批 → 直属领导审批 → HR备案"
3. 将这段内容作为"参考上下文"附在 Prompt 中
4. LLM 基于这段真实文档生成回答

LLM：根据公司 2026 年修订版请假制度，请假流程如下：
1. 登录 OA 系统
2. 选择请假类型（年假/病假/事假）
3. 填写请假的起止时间
4. 提交审批
5. 直属领导审批
6. HR 备案
如遇紧急情况，可先电话通知直属领导，事后 24 小时内在 OA 系统补提申请。

✅ 每一条都是公司文档中的真实内容，不是 LLM 编造的！
```

#### 4.1.3 RAG 的定义

> **RAG（Retrieval-Augmented Generation，检索增强生成）= 先检索相关文档 → 把文档内容作为上下文 → 让 LLM 基于上下文生成回答**

三个关键步骤，每个词都很重要：

| 关键词 | 含义 | 做什么 |
|--------|------|--------|
| **Retrieval（检索）** | 从知识库中找到与用户问题最相关的文档 | 在海量文档中"大海捞针" |
| **Augmented（增强）** | 把检索到的文档拼入 Prompt 中 | 给 LLM"参考资料" |
| **Generation（生成）** | LLM 基于参考资料回答问题 | 给出准确、有据可查的回答 |

**一句话理解**：RAG 就是"给 LLM 开卷考试的权利"——先让它翻书找答案，再让它用自己的语言组织回答。

> 📊 **企业视角：RAG = 2026年企业AI落地的第一站**  
> 
> 为什么是RAG？因为在所有企业AI方案中，它是**唯一同时满足以下五个条件**的技术路线：
> 
> | 维度 | RAG | 微调（Fine-tuning） | 预训练（Pre-training） | 纯Prompt工程 |
> |------|-----|-------------------|----------------------|------------|
> | **部署周期** | 1-2周 | 2-8周 | 3-12个月 | 1-3天 |
> | **日运营成本** | ￥10-100 | ￥50-500 | ￥1000-10000+ | ￥1-50 |
> | **效率提升** | 50-200% | 30-100% | 50-300% | 10-50% |
> | **数据安全** | 数据不出内网 | 数据送云端训练 | 数据送云端训练 | 数据送云端 |
> | **可验证性** | 答案有明确来源 | 答案来自模型"记忆" | 答案来自模型"知识" | 答案来自模型"知识" |
> | **更新周期** | 实时（更新文档即可） | 按周/月（重新训练） | 按月/季度 | 实时（改Prompt） |
> | **技术门槛** | 低（Python基础即可） | 中（需ML经验） | 极高（需AI团队） | 极低 |
> | **初始投入** | ￥0-5万 | ￥10-50万 | ￥500万-5000万+ | ￥0 |
> 
> **企业RAG的战略定位**：
> - RAG不是"最好的AI技术"，但是"性价比最高、风险最低、见效最快"的企业AI方案
> - 对于90%的企业（年营收5亿以下），RAG是**唯一值得投入的AI基础设施**
> - 建议路径：先用RAG做1-2个场景跑通ROI→再考虑是否升级到微调→预训练几乎不需要

### 4.2 RAG 工作流程详解

RAG 的完整工作流程分为两大阶段：**离线阶段（建库）** 和 **在线阶段（问答）**。

```
┌─────────────────────────────────────────────────────────────────────┐
│                        RAG 完整工作流程                                │
│                                                                     │
│  ════════════════ 离线阶段：建立知识库 ════════════════                │
│                                                                     │
│  文档文件（PDF/Word/TXT/MD）                                         │
│       │                                                             │
│       ▼                                                             │
│  [步骤1] 文档加载 ─── 从文件、URL、数据库中读取原始文本                 │
│       │                                                             │
│       ▼                                                             │
│  [步骤2] 文本分段/Chunking ─── 把长文档切成小段（500-1000字符/段）      │
│       │                         🔑 这是最关键的一步！                  │
│       ▼                                                             │
│  [步骤3] 向量化/Embedding ─── 把每段文本转换成一个向量（一串数字）       │
│       │                         语义相近的文本 → 向量也相近            │
│       ▼                                                             │
│  [步骤4] 存入向量数据库 ─── ChromaDB / FAISS / Milvus                 │
│       │                         支持高效的"相似向量搜索"               │
│       ▼                                                             │
│  ✅ 知识库建好了！                                                    │
│                                                                     │
│  ════════════════ 在线阶段：检索 + 生成 ════════════════              │
│                                                                     │
│  用户提问："公司的年假有多少天？"                                      │
│       │                                                             │
│       ▼                                                             │
│  [步骤1] 问题向量化 ─── 用同一个 Embedding 模型把问题变成向量           │
│       │                                                             │
│       ▼                                                             │
│  [步骤2] 向量相似度搜索 ─── 在向量数据库中找最相似的 K 个文本段          │
│       │                      K 通常取 3-5                            │
│       ▼                                                             │
│  [步骤3] 获取 Top-K 文本段 ─── 找到了最相关的 K 段文档内容              │
│       │                                                             │
│       ▼                                                             │
│  [步骤4] 拼装 Prompt ─── 检索到的文档 + 用户问题 → 完整 Prompt         │
│       │                                                             │
│       ▼                                                             │
│  [步骤5] LLM 生成回答 ─── 基于检索到的文档内容，生成准确回答            │
│       │                                                             │
│       ▼                                                             │
│  [步骤6] (可选) 返回引用来源 ─── 告诉用户回答依据了哪篇文档              │
│                                                                     │
│  ✅ 回答完成！准确、有据可查、不胡编乱造。                              │
└─────────────────────────────────────────────────────────────────────┘
```

下面我们逐一详细讲解每个步骤。

---

#### 离线阶段详解

##### 步骤 1：文档加载（Document Loading）

把各种格式的文档读入程序，统一处理为纯文本。

**支持的文档来源**：

| 来源 | 示例 | 说明 |
|------|------|------|
| **文本文件** | `.txt`, `.md` | 直接读取，最简单 |
| **PDF 文件** | 公司制度 PDF、论文 | 需要 PyPDF2 或 pdfplumber 解析 |
| **Word 文档** | `.docx` | 需要 python-docx |
| **网页** | 公司官网、Wiki | 可以用 requests + BeautifulSoup |
| **数据库** | MySQL、MongoDB | 直接从数据库查询 |
| **API** | 飞书文档、Notion | 通过 API 获取 |

在本节课的实操中，我们为了简化，直接在代码中定义文档内容（用 Python 字符串）来演示整个流程。如果你后续想加载真实文件，只需要把"文档内容"的获取方式从"写死在代码中"改为"从文件读取"即可。

##### 步骤 2：文本分段 / Chunking（最关键的一步）

这是整个 RAG 系统中**最容易被忽视、但实际上影响效果最大**的一个步骤。

**为什么要分段？**

1. LLM 的上下文窗口有限（虽然现在可以到 128K token，但不能无限塞内容）
2. 整篇文章塞进去 → 太多无关内容 → 干扰 LLM 找到重点
3. 太长的文本做 Embedding → 语义被"平均化" → 检索不精准

**分段大小的权衡**：

```
┌────────────────────────────────────────────────────────────────┐
│                    Chunk Size 大小的影响                         │
│                                                                │
│  太小（如 100 字/段）：                                          │
│    ✅ 检索精确，能精准定位到具体句子                               │
│    ❌ 丢失上下文 —— 一句话脱离段落可能完全变味                     │
│    ❌ 一个问题的答案可能被切成多个片段，信息不完整                  │
│    示例："请假流程如下：1. 登录OA系统"  ← 后半段不知道去哪了        │
│                                                                │
│  太大（如 5000 字/段）：                                         │
│    ✅ 上下文完整，信息不丢失                                      │
│    ❌ 检索不精确 —— 检索到的那一大段里，90% 的内容可能无关          │
│    ❌ LLM 处理时间长，token 消耗大                               │
│    示例：检索到了整本员工手册，但用户只想知道请假流程               │
│                                                                │
│  适中（500-1000 字/段，100-200 字重叠）：                        │
│    ✅ 兼顾检索精度和上下文完整性                                  │
│    ✅ 重叠部分确保关键信息不会在分段边界处被截断                    │
│    ✅ 这是实践经验中效果最好的范围                                 │
└────────────────────────────────────────────────────────────────┘
```

**分段策略对比**：

| 分段策略 | 方法 | 优点 | 缺点 | 适用场景 |
|----------|------|------|------|----------|
| **固定大小分段** | 按字符数等距切分 | 简单、快速、可控制 | 可能在句子中间切断 | 通用场景，最常用 |
| **按句子分段** | 以句号、问号等为边界 | 保持句子完整性 | 各段长度不均匀 | 对话、问答类文档 |
| **按段落分段** | 以换行符为边界 | 保持段落完整性 | 段落可能很长或很短 | 结构化文档 |
| **语义分段** | 用 AI 模型判断语义边界 | 效果最好 | 成本高、速度慢 | 高质量要求的场景 |
| **递归分段** | 先用大分隔符，不够再用小分隔符 | 灵活、效果好 | 实现稍复杂 | LangChain 默认策略 |

**Chunk Overlap（分段重叠）的作用**：

```
不重叠分段（overlap=0）：
  [段落A：...提交审批  | 段落B：直属领导审批...]  ← "提交审批"和"直属领导审批"被分开了！

有重叠分段（overlap=100）：
  [段落A：...OA系统 → 提交审批 → 直属领导审批 → HR备案...]
  [段落B：...提交审批 → 直属领导审批 → HR备案 → 事后24小时...]
  ↑ 重叠部分保证了关键信息同时出现在两个段落中，不会因分段边界而丢失上下文
```

**本节实操采用的分段策略**：固定 500 字符/段 + 100 字符重叠，这是入门学习的最佳平衡点。

##### 步骤 3：向量化 / Embedding

这是 RAG 最核心的技术概念。不要被"向量"这个词吓到，它其实非常直观。

**什么是 Embedding？**

> Embedding = 把一段文本"翻译"成一串数字（向量），使得**语义相近的文本，它们的向量在数学上也相近**。

**直观理解**：

```
想象一个二维平面（实际向量通常是 384 或 768 或 1536 维）：

        "请假"
         ●
          ↘
           "年假申请"  ●
                        ↘
        "如何请假"  ●────→  "病假怎么请" ●
                                        ↗
                          "发烧请假" ●

你会发现：
- "请假"相关的所有文本，它们的向量点都聚集在某个区域
- "报销"相关的文本，向量点聚集在另一个区域
- "入职"相关的文本，又在另一个区域

这就是 Embedding 的神奇之处：把语义相似性变成了数学上的距离！
```

**Embedding 模型选择**：

| 模型 | 提供方 | 向量维度 | 价格 | 中文支持 | 推荐场景 |
|------|--------|----------|------|----------|----------|
| `paraphrase-multilingual-MiniLM-L12-v2` | Sentence-Transformers (本地) | 384 | **免费** | ✅ 好 | 学习、小型项目 |
| `text-embedding-3-small` | OpenAI API | 1536 | ~$0.02/1M tokens | ✅ 好 | 生产环境、要求高精度 |
| `text-embedding-3-large` | OpenAI API | 3072 | ~$0.13/1M tokens | ✅ 最好 | 对精度要求极高的场景 |
| `bge-large-zh-v1.5` | BAAI (本地) | 1024 | **免费** | ✅ 很好 | 中文为主的场景 |

**本地模型 vs API 模型的权衡**：

| 维度 | 本地模型 (sentence-transformers) | API 模型 (OpenAI) |
|------|----------------------------------|-------------------|
| **费用** | 免费 | 按量付费（但很便宜） |
| **隐私** | 数据不出本机，完全隐私 | 文本发送到云端 |
| **速度** | 依赖本机 CPU/GPU | 云端高速 GPU |
| **精度** | 中等 | 高 |
| **部署** | 需要下载模型文件（~500MB） | 有网就行 |
| **推荐人群** | 学习阶段、数据敏感场景 | 生产环境、追求效果 |

> **本节课选择本地模型**：`paraphrase-multilingual-MiniLM-L12-v2`，原因：
> 1. 免费 —— 学生不需要花钱
> 2. 支持中文 —— 满足中文知识库需求
> 3. 384 维向量 —— 轻量，本机 CPU 也跑得动
> 4. 下载一次即可 —— 首次使用会自动下载模型（约 500MB），后续使用秒级加载

**代码演示：直观感受 Embedding**：

```python
from sentence_transformers import SentenceTransformer

# 加载本地模型（首次运行会自动下载）
model = SentenceTransformer('paraphrase-multilingual-MiniLM-L12-v2')

# 三句话：两句相似，一句不同
text1 = "公司的请假流程是什么？"
text2 = "怎么申请年假？"
text3 = "今天天气真好"

# 生成 Embedding
emb1 = model.encode(text1)
emb2 = model.encode(text2)
emb3 = model.encode(text3)

# 计算相似度（余弦相似度，-1 到 1，越大越相似）
from numpy import dot
from numpy.linalg import norm

def cosine_similarity(a, b):
    return dot(a, b) / (norm(a) * norm(b))

print(f"text1 vs text2 相似度: {cosine_similarity(emb1, emb2):.4f}")  # 预期：0.7~0.9（很相似）
print(f"text1 vs text3 相似度: {cosine_similarity(emb1, emb3):.4f}")  # 预期：0.1~0.3（不相似）
```

运行这段代码你会看到：
- "请假流程" 和 "申请年假" 的相似度很高（0.7+），因为它们语义相关
- "请假流程" 和 "今天天气真好" 的相似度很低（0.3 以下），因为它们语义无关

这就是 Embedding 的核心能力：**把语义相似变成了数学上的距离相近**。

##### 步骤 4：存入向量数据库

向量数据库专门用来存储向量，并支持高效的"相似向量搜索"。

**为什么不能用普通数据库？**

普通数据库（如 MySQL）擅长精确查询：`SELECT * FROM docs WHERE title = '请假制度'`。但在 RAG 中，用户的提问和文档的内容不可能一模一样。我们需要的是"意思相近"的查询，这就是向量数据库的专长。

**常用向量数据库对比**：

| 数据库 | 类型 | 部署难度 | 性能 | 适用场景 |
|--------|------|----------|------|----------|
| **ChromaDB** | 轻量嵌入式 | ⭐ 极简（pip install 即用） | 中等 | 学习、原型、小型项目 |
| **FAISS** | 本地库 | ⭐⭐ 简单 | ⭐⭐⭐ 很快 | 中型项目、研究 |
| **Milvus** | 企业级 | ⭐⭐⭐⭐ 较复杂 | ⭐⭐⭐⭐ 高性能 | 大规模生产环境 |
| **Pinecone** | 云服务 | ⭐ 零部署 | ⭐⭐⭐⭐ | 不想管运维的场景 |
| **Qdrant** | 开源 | ⭐⭐ 简单 | ⭐⭐⭐ | 中小型生产环境 |

> **本节课选择 ChromaDB**：它是 Python 原生、pip install 即用、API 简单直观，学习成本极低。代码方面只需要几行就能完成建库和检索。

#### 在线阶段详解

##### 步骤 1：问题向量化

用户输入问题后，用**与离线阶段完全相同的 Embedding 模型**把问题转换为向量。

> ⚠️ **重要**：离线建库和在线检索必须使用同一个 Embedding 模型！因为不同模型的向量空间不同，不能混合使用。用模型 A 建的库，必须用模型 A 检索。

##### 步骤 2：相似度搜索

在向量数据库中搜索与问题向量最相似的 K 个文本段。

**K 值怎么选？**

| K 值 | 效果 | 适用场景 |
|------|------|----------|
| K=1 | 只返回最匹配的一个段落 | 答案很明确地存在于单一位置 |
| **K=3~5** | **最常用的选择** | 答案可能分散在多个段落中 |
| K=10+ | 返回很多结果，信息更全面 | 复杂问题，但可能引入更多噪音 |

**相似度计算方法**：

向量之间的"距离"或"相似度"有多种计算方式：

| 方法 | 公式思路 | 值范围 | 特点 |
|------|----------|--------|------|
| **余弦相似度** (Cosine Similarity) | 两个向量夹角的余弦 | -1 到 1 | 最常用，只关心方向不关心长度 |
| **欧氏距离** (Euclidean Distance) | 两点间的直线距离 | 0 到 +∞ | 越接近 0 越相似，受向量长度影响 |
| **点积** (Dot Product) | 对应元素相乘再求和 | -∞ 到 +∞ | 计算最快，适合大规模检索 |

在 ChromaDB 中，默认使用余弦相似度，这是最广泛使用的方法。

##### 步骤 3-4：拼装 Prompt + LLM 生成

这是 RAG 的"Generation"部分。把检索到的文档内容作为参考上下文，和用户的问题一起放入 Prompt 中。

### 4.3 RAG 的 Prompt 模板

一个好的 RAG Prompt 决定了 LLM 是否真的会"认真看"提供的上下文，还是忽略它继续靠自己（不确定的）知识来回答。

#### 4.3.1 标准的 RAG Prompt 模板

```
System Prompt:
──────────────────────────────────────────────────────────
你是一个专业的 AI 助手。请严格根据以下提供的知识库内容回答用户的问题。

【重要规则】
1. 只使用下面"知识库内容"中的信息来回答，不要使用你自己的知识
2. 如果知识库内容足以回答问题，请给出完整、准确的回答
3. 如果知识库内容不足以回答问题，请明确回复：
   "抱歉，根据当前知识库的内容，我无法回答这个问题。建议您查阅相关文档或联系相关部门。"
4. 回答时请引用具体的数据、条款或流程
5. 不要编造任何知识库中不存在的信息

【知识库内容】
{context}

【用户问题】
{query}
──────────────────────────────────────────────────────────
```

#### 4.3.2 一个好的 RAG Prompt 的关键要素

| 要素 | 作用 | 如果不写会怎样 |
|------|------|---------------|
| **角色定义** | 让 LLM 进入正确的工作模式 | LLM 可能以闲聊模式回复 |
| **"只使用知识库内容"** | 限制 LLM 不要用自身知识 | LLM 可能混合自身知识和检索内容，产生幻觉 |
| **"不知道就直说"** | 防止 LLM 在检索不到时编造 | LLM 倾向于"一直说话"，不知道也会编 |
| **"引用具体信息"** | 提高回答的可信度 | 回答可能模糊，无法追溯来源 |
| **"不要编造"** | 直接约束幻觉行为 | LLM 有时"好心办坏事"，编造看起来合理的内容 |

#### 4.3.3 好 vs 差的 RAG Prompt 对比

**差的 Prompt** ❌：
```
你是一个助手，请根据以下内容回答问题。
内容：{context}
问题：{query}
```
问题：太随意了，LLM 不知道优先使用上下文还是自身知识。

**好的 Prompt** ✅：
```
你是公司内部知识库 AI 助手。你必须严格按照以下文档内容回答用户问题，
不得使用文档之外的信息。如果文档中没有相关信息，请明确告知用户。

参考文档：
{context}

用户问题：{query}

请给出准确、有据可查的回答，引用文档中的具体条款。
```

### 4.4 检索策略进阶

基础的 Top-K 相似度搜索在大多数场景下已经够用，但在实际项目中，你可能需要以下高级策略：

#### 4.4.1 MMR（Maximal Marginal Relevance，最大边际相关性）

**问题**：Top-K 检索可能返回 K 个内容几乎相同的段落（比如同一政策的 3 个不同表述），浪费了宝贵的上下文空间。

**MMR 解决思路**：选择的结果既要"与问题相关"，又要"彼此之间不重复"。

```
MMR 选择策略：
1. 先检索 Top-N（N > K，比如 N=20）个候选结果
2. 从候选中逐一选出最终结果：
   - 第 1 个：选与问题最相似的
   - 第 2 个：选"既与问题相关，又与第 1 个不太相似"的
   - 第 3 个：选"既与问题相关，又与第 1、2 个不太相似"的
   - ...
3. 选出 K 个"相关且多样"的最终结果
```

#### 4.4.2 Re-ranking（重排序）

**思路**：先用速度快的 Embedding 模型做粗筛（比如从 10000 段中选出 50 段），再用一个更强大的模型对 50 段做精细排序，最终给出最相关的 Top-K。

```
粗筛（快速 Embedding 模型）        精排（强模型）
10000 段  ──────────────────→  50 段  ──────────→  5 段
  速度快、精度低                   速度慢、精度高
```

**为什么需要 Re-ranking？**

- Embedding 模型把长文本压缩为固定维度的向量时，一定会丢失一些细节信息
- Re-ranking 模型可以逐字逐句对比用户问题和候选文档，判断得更准
- 折中方案：用快速模型过滤大量无关内容，再用强模型做最终判断

#### 4.4.3 混合检索（Hybrid Search）

| 检索方式 | 原理 | 优点 | 缺点 |
|----------|------|------|------|
| **关键词检索（BM25）** | 基于词频和逆文档频率匹配 | 精确匹配关键词，不会漏掉专业术语 | 不理解语义，"请假"和"休假"算作两个词 |
| **语义检索（Embedding）** | 基于语义相似度 | 理解同义词、改写、上下文 | 可能漏掉精确的专有名词匹配 |

**混合检索 = BM25 + 语义检索**，将两种检索结果融合排序，取长补短。

> 对于本节课的学习阶段，基础 Top-K 就完全够用了。进阶策略留在你后续深入 RAG 开发时再探索。

### 4.5 RAG 的常见问题与优化

| 常见问题 | 可能原因 | 解决方案 |
|----------|----------|----------|
| **检索结果不相关** | Chunk 太大或太小 | 调整 chunk_size 和 overlap |
| | Embedding 模型不合适 | 换用更强的模型，或选中文专用模型 |
| | K 值设置不当 | 尝试 K=3, 5, 7 对比效果 |
| **回答不基于文档（幻觉）** | Prompt 约束不够 | 强调"只使用提供的文档内容"，加"不知道就说不知道" |
| | 检索结果与问题不相关 | LLM 没找到有用信息就自己发挥了 |
| **上下文太长超限** | 检索了太多片段 | 减少 K 值，或对检索结果做截断 |
| | 单个 Chunk 太大 | 压缩 chunk_size |
| **文档更新后旧答案还在** | 向量数据库没有更新 | 文档变更后需要重新 Indexing（删除旧向量 + 添加新向量） |
| **跨文档的信息无法关联** | 分段割裂了文档间的联系 | 考虑用知识图谱或 Chunk 之间加元数据关联 |
| **专业术语检索不到** | Embedding 模型不理解专业词汇 | 用混合检索（BM25+Embedding），BM25 能精准匹配关键词 |

> **最重要的调优经验**：在 RAG 系统中，**检索质量决定了回答质量的上限**。如果检索阶段就没找到正确的文档，LLM 再强也答不对。所以在优化 RAG 时，优先优化检索环节（Chunking 策略、Embedding 模型、检索参数），其次才是优化 Prompt。

### 4.6 企业RAG决策框架

> 📊 **企业视角：什么场景用RAG vs 微调 vs 预训练？**  
> 
> 这是企业AI投入的核心决策矩阵。选择错误 = 浪费几十万甚至几百万。
> 
> | 判断维度 | → 选RAG | → 选微调 | → 选预训练 |
> |----------|---------|---------|-----------|
> | **知识更新频率** | 频繁（每周/每天） | 偶尔（每月/每季度） | 很少（半年/一年） |
> | **知识量规模** | 大（1万+文档） | 中（1000-10000条QA对） | 极大（TB级文本） |
> | **回答风格需求** | 通用风格即可 | 需要定制口吻/格式 | 需要完全独特的风格 |

> **决策口诀**：
> - 知识频繁变 → RAG（文档改了就生效）

> - 预训练 → 除非你是OpenAI/DeepSeek级别的公司，否则不需要考虑

### 实操 1：搭建简易 RAG 知识库（45 分钟）

**目标**：从零搭建一个完整可运行的 RAG 知识库问答系统，理解每一步做了什么。

#### 第 1 步：导入库和基础配置

```python
# ============================================

# --- 1.2 配置 API ---
# 方案A：使用 DeepSeek（推荐国内学生，性价比高）
llm_client = OpenAI(
    api_key="your-deepseek-api-key",     # 替换为你的 API Key
```

#### 第 3 步：文本分段（Chunking）

```python
# --- 3.1 实现分段函数 ---
def split_text(text, chunk_size=500, overlap=100):
    """
    将长文本按照固定大小分段，相邻段之间有重叠。

    参数：
        text: 要分段的原始文本（字符串）
        chunk_size: 每段的最大字符数（默认 500）
        overlap: 相邻段之间的重叠字符数（默认 100）

    返回：
        分段后的文本列表

    举个例子：
        文本："ABCDEFGHIJKLMNOPQRSTUVWXYZ"（26个字符）
        chunk_size=10, overlap=3
        返回：
        ["ABCDEFGHIJ",   ← 字符 0~10
         "HIJKLMNOPQ",   ← 字符 7~17（"HIJ" 与上一段重叠）
         "OPQRSTUVWX",   ← 字符 14~24（"OPQ" 与上一段重叠）
         "VWXYZ"]        ← 字符 21~26（"VWX" 与前一段重叠）
    """
    chunks = []
    start = 0
    text_length = len(text)

    while start < text_length:
        end = start + chunk_size
        chunk = text[start:end].strip()
        if chunk:  # 忽略空白段
            chunks.append(chunk)
        start = end - overlap  # 下一段的起始位置，减去 overlap 实现重叠
        # 防止死循环（当 overlap >= chunk_size 时）
        if start <= 0 or start >= text_length:
            break

    return chunks


# --- 3.2 对所有文档进行分段 ---

    # 每个文档单独分段

    for chunk in chunks:
        # 每个分段保留来源文档名称，方便后续引用
        all_chunks.append({
            "source": doc["title"],   # 来源文档标题
            "content": chunk          # 分段后的文本内容
        })
```

```python
# --- 6.1 RAG 问答函数 ---
def rag_answer(query, top_k=3, verbose=True):
    """
    RAG 问答的完整流程：检索 → 拼装 Prompt → LLM 生成

    参数：
        query: 用户提问
        top_k: 检索多少个相关文本段
        verbose: 是否打印检索到的参考文档

    返回：
        LLM 生成的回答（字符串）
    """
    # ── 阶段 1：检索 ──
    search_results = search_knowledge(query, top_k=top_k)

    # 把检索到的文本段拼成"参考上下文"
    context_parts = []
    for i, (doc, meta, dist) in enumerate(zip(
        search_results['documents'][0],
        search_results['metadatas'][0],
        search_results['distances'][0]
    )):
        context_part = f"""
【参考文档 {i+1}】
来源：{meta['source']}
内容：
{doc}
"""
        context_parts.append(context_part)

    context = "\n".join(context_parts)

    if verbose:
        print("\n📚 检索到的参考文档：")
        for i, meta in enumerate(search_results['metadatas'][0]):
            print(f"   {i+1}. {meta['source']}（相似度距离: {search_results['distances'][0][i]:.4f}）")

    # ── 阶段 2：拼装 Prompt ──
    system_prompt = f"""你是一个专业的公司内部 AI 助手。你必须严格按照以下提供的知识库文档内容来回答用户的问题。

【核心规则 —— 务必遵守】
1. 只使用下面"知识库参考内容"中的信息来回答问题。
2. 绝对不要使用你自己的常识或外部知识来补充。
3. 如果知识库内容足以回答，请给出完整、准确、有条理的回答。
4. 如果知识库内容不足以回答（信息缺失或不完整），请明确回复：
   "抱歉，根据当前知识库的内容，我暂时无法完整回答这个问题。建议您查阅公司官方文档或咨询 HR 部门。"
5. 回答时请引用知识库中的具体数据和条款，增加可信度。
6. 严禁编造任何知识库中不存在的信息！

【知识库参考内容】
{context}"""

    # ── 阶段 3：调用 LLM 生成回答 ──
    response = llm_client.chat.completions.create(
        model=LLM_MODEL,
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": query}
        ],
        temperature=0.3,   # 较低的温度让回答更确定、减少随机性
        max_tokens=1000    # 限制回答长度
    )

    answer = response.choices[0].message.content
    return answer
```

## 八、常见问题

### Q1：ChromaDB 和 FAISS 我该选哪个？

**A**：对于学习和小型项目，选 ChromaDB。它 Python 原生、API 简洁、不需要额外安装 C++ 依赖。FAISS 在查询速度上有优势（特别当数据量超过 10 万条时），但 API 稍复杂一些。进入生产环境后，如果对性能有要求，可以考虑 FAISS 或 Milvus。

### Q2：Embedding 模型一定要用本地的吗？

**A**：不一定。学习阶段用本地模型是为了免费、省事。在实际项目中：
- 数据敏感（医疗、金融、内部文档）→ 用本地模型
- 追求效果 → OpenAI text-embedding-3-large 效果最好
- 中文为主 → BAAI 的 `bge-large-zh-v1.5` 是很好的本地选择

### Q3：Chunk Size 到底设置多少最好？

**A**：没有放之四海皆准的数字，取决于你的文档类型：
- 制度文档、FAQ：500-800 字符（内容比较结构化、独立性强）
- 长篇报告、论文：800-1500 字符（需要更多上下文）
- 对话记录：300-500 字符（每段对话独立性强）
- 最好的方法是：用不同大小测试，看检索结果的相关性

### Q4：为什么我的检索结果总是不相关？

**A**：按以下顺序排查：
1. Chunk 太大？→ 减小 chunk_size
2. Chunk 太小？→ 增大 chunk_size（特别是在句子中间切断了）
3. Embedding 模型不适合中文？→ 换 BAAI 的中文模型
4. 相似度阈值太低？→ 检查检索结果的 distance 值
5. 文档内容太杂？→ 先对文档做清洗（去掉无关内容、格式字符）

### Q5：多轮对话怎么做？

**A**：核心思路是把对话历史也放进 Prompt 中。两种方式：
1. **上下文检索**：把上一轮对话和当前问题一起做 Embedding 去检索
2. **历史拼入 Prompt**：在 System Prompt 中加入对话历史，让 LLM 知道之前聊了什么
3. 最简单的方式：把历史消息直接放入 messages 列表中（和普通多轮对话一样），同时每一轮都做新的检索。

### Q6：RAG 和 Fine-tuning 有什么区别？什么时候用哪个？

**A**：
- **RAG**：知识存在外部数据库，不改模型参数。适合"知识频繁更新"、"知识量大"、"需要引用来源"的场景。
- **Fine-tuning**：知识"写入"模型参数。适合"风格/语气定制"、"固定知识教学"、"需要降低延迟"的场景。
- **最佳实践**：先用 RAG 解决知识问题，如果效果不够好，再考虑 RAG + Fine-tuning 的组合。

### Q7：如果 Embedding 模型下载失败怎么办？

**A**：
1. 检查网络连接（模型托管在 HuggingFace，部分地区可能需要科学上网）
2. 尝试用国内镜像：设置环境变量 `export HF_ENDPOINT=https://hf-mirror.com`
3. 或者手动下载模型文件放到本地目录，然后用 `SentenceTransformer('./local-model-path')` 加载
4. 如果实在无法使用本地模型，可以临时改为 OpenAI Embedding API

### Q8：RAG 的知识库可以有多大？

**A**：
- ChromaDB（内存模式）：适合几千到几万条数据（学习和小型项目够了）
- ChromaDB（持久化）：可以到几十万条
- FAISS：百万级别没问题
- Milvus / Pinecone：亿级别
- 对于课程作业，5-10 篇文档完全够用，性能不是瓶颈

### 💼 企业常见问题

**Q9: 企业部署RAG需要什么样的技术团队？**

A: 基本配置（MVP阶段）：1名Python开发者（熟悉API调用和基础数据库操作）+ 1名业务专家（整理知识库文档）。不需要AI/ML背景。生产环境扩展需要增加：1名后端工程师（API优化、缓存、监控）+ DevOps支持（容器化部署、CI/CD）。

**Q10: RAG系统的长期维护成本高吗？**

A: RAG的维护成本集中在三个方面：
1. **知识库更新**（占维护成本的60%）：随着业务文档增长，需要持续整理、清洗、重新索引。建议指定一名业务人员兼职负责（约占用20%工作时间）
2. **Prompt和参数调优**（占30%）：随着使用量增长，需要根据用户反馈不断优化检索策略和Prompt模板
3. **系统运维**（占10%）：服务器、API Key管理、监控告警等基础运维

月度维护总成本估算：中型应用（10万+文档）约￥1,500-5,000/月（含API费用）。相比人工处理的成本，维护费用通常不到节省金额的5%。

**Q11: 如何说服管理层投入RAG项目？**

A: 建议用"三页PPT"策略：
- **第1页：痛点**——展示一个具体的低效场景（如"客服每天花2小时在内部文档中翻找答案"），附上数据（月度人工成本、响应时间、错误率）
- **第2页：RAG方案**——用本课的案例做类比（"某律所用RAG后审查效率提升75%"），说明技术原理（1分钟大白话解释）
- **第3页：试点方案**——提出一个为期3周、预算￥1-3万的POC（概念验证）项目，用一个小范围的知识库先跑出效果数据

管理层最怕的是"AI黑箱"和"预算黑洞"。RAG的优势在于：**可验证（答案有来源）、低成本（不会超过预算）、见效快（2周出结果）**——这三点恰恰是说服管理层的利器。

**Q12: RAG系统的回答质量如何保证？有没有衡量标准？**

A: 企业评估RAG质量通常用以下指标：
1. **检索命中率**：检索到的文档中，真正包含问题答案的比例（目标 > 80%）
2. **回答准确率**：AI生成的回答中，信息完全正确的比例（目标 > 90%）
3. **拒答率**：知识库中没有相关信息时，AI正确说"不知道"而非编造的比例（目标 > 95%）
4. **用户满意度**：通过用户评分（点赞/踩）和重复使用率衡量

建议在POC阶段就建立评估基线：邀请5名业务专家，每人问20个问题，统计以上四项指标。上线后持续追踪并每月通报。
