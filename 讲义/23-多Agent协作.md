## 四、核心知识点详解

### 4.1 为什么需要多Agent？

#### 4.1.1 单Agent的天然天花板

一个单Agent（哪怕模型再强）面对复杂任务时，会遇到四个根本限制：

**限制一：上下文过载（Context Overload）**

一个Agent的上下文窗口是有限的。如果你让一个Agent同时承担"搜索资料 + 分析数据 + 撰写报告 + 检查错误 + 排版美化"五种职责，它的system prompt会变得非常臃肿。当prompt超过几千字后，模型会"忘记"早期指令，注意力被稀释，输出质量断崖式下降。

这就好比让一个人同时扮演产品经理、设计师、程序员和测试工程师 —— 他可能在每个角色上都表现平平，而不是在每个角色上都很出色。

**限制二：指令冲突（Conflicting Instructions）**

一个典型的矛盾："你是严谨的学术研究者，必须引用所有来源" vs "你是流畅的通俗写作者，要让小学生也能看懂"。这两条指令放在同一个prompt里，模型会左右为难。学术风格和通俗风格需要的是两种截然不同的写作策略，混在一起就是"既要又要"，结果往往是"两边不讨好"。

**限制三：单一视角（Single Perspective）**

一个Agent只有一个"思维模式"。它很难在"创造性发散"和"批判性审视"之间自由切换 —— 因为这本质上是两种不同的认知过程。就像一个作者很难同时做好自己的编辑：写的时候你觉得每个观点都精彩绝伦，但换一个视角审视，漏洞百出。

**限制四：无法并行（No Parallelism）**

单Agent只能串行执行：先搜索、再阅读、再思考、再写作。如果一个任务需要同时从不同角度搜集信息（比如"从法律角度"和"从技术角度"同时调研一个话题），单Agent只能一个接一个做，耗时很长。

#### 4.1.2 多Agent的优势

多Agent的核心理念很简单：**把复杂任务拆解成多个子任务，每个子任务交给一个专门的Agent处理。**

| 优势 | 说明 | 类比 |
|------|------|------|
| **专业化（Specialization）** | 每个Agent只聚焦一个职责，prompt短而精，表现更好 | 医院分科室：内科、外科、儿科各司其职 |
| **并行执行（Parallel Execution）** | 互不依赖的子任务可以同时进行，缩短总时间 | 建房子：水电和墙面可以同时施工 |
| **多元视角（Diverse Perspectives）** | 不同Agent从不同角度审视同一问题，互相补充 | 论文答辩：多位评委从不同角度提问 |
| **制衡机制（Checks and Balances）** | 一个Agent的输出可以被另一个Agent审核和纠正 | 代码审查：写代码的人不能自己批准合并 |

#### 4.1.3 多Agent的代价 —— 不要盲目上多Agent

多Agent不是银弹。以下代价必须清醒认识：

| 代价 | 说明 |
|------|------|
| **更高复杂度** | 需要设计Agent之间的通信协议、数据格式、错误处理、超时机制 |
| **更高成本** | 多个Agent = 多次API调用 = 更多token消耗。四个Agent各调用一次，成本至少是单Agent的四倍 |
| **更难调试** | 输出出问题时，你需要逐层排查是哪个Agent出了问题，而不是只查一个prompt |
| **延迟叠加** | 串行模式下，总延迟 = 各Agent延迟之和；即使并行，也需要等待最慢的那个 |
| **协调失败** | Agent之间可能出现循环争论（两个Agent互相纠正，永远无法达成一致）、任务漂移（Agent偏离原始目标越跑越远）、上下文膨胀（每个Agent的输出都堆给下一个Agent，总token数指数增长） |

#### 4.1.4 黄金法则：先用单Agent，实在不行再上多Agent

这是本节课最重要的一条原则，没有之一：

> **一个设计精良的单Agent > 一个设计粗糙的多Agent系统**

决策流程如下：

```
任务来了
    │
    ▼
┌─────────────────────┐
│ 单Agent能搞定吗？    │
│ 判断标准：           │
│ 1. prompt < 1000字? │
│ 2. 任务边界清晰?    │
│ 3. 不需要多角度审视? │
└──────┬──────────────┘
       │
   ┌───┴───┐
   │ 能    │ 不能
   ▼       ▼
用单Agent  问：拆解成多个子任务后，
           每个子任务是否有明确的
           不同职责？
              ┌───┴───┐
              │ 是    │ 否
              ▼       ▼
          用多Agent  重新设计单Agent的prompt
```

**判断能否用单Agent的三个条件**：

1. **Prompt够短**：把所有指令写进一个system prompt，不超过1000字，模型能稳定遵循
2. **任务边界清晰**：输入是什么、输出是什么、中间不需要"自我纠错"循环
3. **单一视角够用**：不需要批判者角色，不需要从多个不同立场审视

如果三个条件都满足，**就用单Agent**。只有在以下情况下才考虑多Agent：

- 任务天然需要多个专业领域（法律+技术+商业）
- 任务需要"生成-审核-修改"这种天然的质量控制循环
- 任务的不同部分互不依赖，可以并行加速
- 单Agent反复尝试后输出质量仍然不达标

### 4.2 四种多Agent协作模式

多Agent协作的核心问题只有一个：**Agent之间如何通信和协调？** 围绕这个问题，业界沉淀出了四种经典模式。这四种模式没有绝对的优劣之分，关键在于：**为你的场景选对模式。**

---

#### 4.2.1 模式一：顺序协作（Pipeline / Sequential）

**核心思想**：像工厂流水线，Agent A处理完 → 交给Agent B → 交给Agent C → 最终输出。

```
┌──────────┐     ┌──────────┐     ┌──────────┐     ┌──────────┐
│ Agent A  │────>│ Agent B  │────>│ Agent C  │────>│ 最终输出  │
│ Researcher│     │  Writer  │     │ Reviewer │     │          │
└──────────┘     └──────────┘     └──────────┘     └──────────┘
   搜索资料          撰写初稿          审核修改          定稿
```

**工作流程**：
1. Agent A 接收初始输入，完成自己的工作，产出结构化输出
2. Agent B 接收 A 的输出作为输入，在此基础上完成自己的工作
3. Agent C 接收 B 的输出作为输入，完成最终加工
4. 输出最终结果

**典型例子 —— Researcher → Writer → Reviewer → Reviser**：

- **Researcher（研究员）**：接收主题，搜索并整理相关资料，输出结构化研究笔记
- **Writer（写作者）**：接收研究笔记，撰写初稿
- **Reviewer（审稿人）**：接收初稿，从结构、逻辑、语言角度审核，输出修改建议
- **Reviser（修改者）**：接收初稿+修改建议，输出最终定稿

**优点**：
- 流程简单直观，容易理解和实现
- 每个Agent的职责非常明确
- 输出可预测，调试时逐环节排查即可

**缺点**：
- 无法并行 —— 每个环节必须等上一个完成
- 单点故障 —— 中间任何一个Agent出问题，整条线都废了
- 错误会传导和放大 —— A 的错误数据会被 B 写进正文，C 审核时可能没发现

**适用场景**：
- 任务本身具有天然的阶段性（研究→写作→审核→修改）
- 对并行性没有要求
- 团队刚开始接触多Agent，需要一个容易上手的模式

> 📊 **企业视角：多Agent协作 = 企业的 AI"部门"**
>
> 将多Agent模式映射到企业组织：
>
> | 多Agent模式 | 企业组织类比 | 典型企业场景 | AI团队成本（vs人类团队） |
> |------------|------------|-------------|----------------------|
> | **顺序式** | 流水线 | 采购审批链（申请→审核→批准→执行） | ¥1,500/月 vs ¥50,000/月（4人） |
> | **监督式** | 经理+执行团队 | 市场调研（分配任务→并行调研→汇总报告） | ¥2,000/月 vs ¥60,000/月（5人） |
> | **辩论式** | 评审委员会 | 投资决策分析（多方独立评估→交叉验证→综合结论） | ¥3,000/月 vs ¥80,000/月（6人） |
> | **分层式** | 公司组织架构 | 软件项目开发（PM→前端+后端+测试） | ¥4,000/月 vs ¥120,000/月（10人） |
>
> **核心洞察**：多Agent不是让AI"更聪明"，而是让AI**以更低成本模拟高效团队协作**——24×7工作、无沟通损耗（不会吵架）、成本是同等人类团队的1/10-1/50。

#### 4.2.2 模式二：监督式协作（Supervisor）

**核心思想**：有一个"主管"Agent负责拆解任务、分配给不同的"工人"Agent、收集结果并合成最终输出。

```
                    ┌──────────────┐
                    │  Supervisor  │
                    │   主管Agent   │
                    │  拆解+分配+合成 │
                    └───┬──┬──┬───┘
                        │  │  │
            ┌───────────┘  │  └───────────┐
            ▼              ▼              ▼
      ┌──────────┐  ┌──────────┐  ┌──────────┐
      │ Worker A │  │ Worker B │  │ Worker C │
      │  法律专家  │  │  技术专家  │  │  商业专家  │
      └──────────┘  └──────────┘  └──────────┘
            │              │              │
            └──────────────┼──────────────┘
                           ▼
                    ┌──────────────┐
                    │  Supervisor  │
                    │  收集+审查+合成 │
                    └──────┬───────┘
                           ▼
                       最终输出
```

**工作流程**：
1. 用户把任务交给 Supervisor
2. Supervisor 分析任务，拆解成 N 个子任务
3. Supervisor 决定把每个子任务分配给哪个 Worker
4. 各个 Worker 可以**并行**执行（这是相比顺序模式的最大优势）
5. Supervisor 收集所有 Worker 的结果
6. Supervisor 审查质量，如果不满意，退回重做
7. Supervisor 将所有结果合成为最终输出

**典型例子 —— Supervisor 拆解"开一家咖啡馆的商业计划"**：

- Supervisor 拆解子任务：市场调研（Worker A）、财务分析（Worker B）、选址策略（Worker C）、营销方案（Worker D）
- 四个 Worker 并行工作
- Supervisor 收集四份报告，审查数据一致性，合成一份完整商业计划书

**优点**：
- 集中控制，全局可控 —— Supervisor 掌握全貌
- 子任务可以并行，节省时间
- 有利于复杂任务的分解（Supervisor 具备"全局视野"）
- Worker 之间不需要互相通信，降低耦合

**缺点**：
- Supervisor 是瓶颈 —— 如果 Supervisor 分析能力不够，整个系统垮掉
- Supervisor 需要很强的"任务拆解"和"质量判断"能力，对模型要求高
- 如果拆解不合理（粒度太粗或太细），Worker 的输出会偏离预期
- Supervisor 一次调用要处理所有 Worker 的输出，容易上下文膨胀

**适用场景**：
- 复杂任务可以被拆解为多个相对独立的子任务
- 需要一个"把关人"来确保整体质量
- 子任务之间不需要互相知道对方在做什么

#### 4.2.3 模式三：辩论式协作（Debate）

**核心思想**：多个Agent从不同角度独立解决问题，然后互相"辩论"（critique），在争论中收敛到更好的答案。

```
┌──────────────┐     ┌──────────────┐
│   Agent A    │     │   Agent B    │
│  方案A生成者  │     │  方案B生成者  │
└──────┬───────┘     └──────┬───────┘
       │                    │
       ▼                    ▼
  ┌─────────────────────────────────┐
  │         互相 Critique            │
  │  A 指出 B 方案的漏洞             │
  │  B 指出 A 方案的不足             │
  └────────────┬────────────────────┘
               │
               ▼
  ┌─────────────────────────────────┐
  │       各自根据 Critique 修改      │
  └────────────┬────────────────────┘
               │
               ▼
  ┌─────────────────────────────────┐
  │     是否达成共识 / 达到最大轮次？  │
  └──────┬──────────────┬───────────┘
         │              │
     是  │              │  否（回到互相Critique）
         ▼              ▼
    输出最优方案     继续辩论
```

**工作流程**：
1. 两个（或多个）Agent 各自独立生成一个方案
2. 每个 Agent 拿到其他 Agent 的方案，进行 critique（批判性分析）
3. 每个 Agent 根据收到的 critique 修改自己的方案
4. 重复步骤 2-3，直到：
   - 达成共识（方案趋同），或
   - 达到最大迭代轮次（防止无限循环），或
   - 裁判 Agent 判定某个方案胜出

**典型例子 —— 解一道复杂的数学证明题**：

- Agent A 用代数方法尝试证明
- Agent B 用几何方法尝试证明
- A 检查 B 的证明，发现"第3步到第4步的过渡不严谨"
- B 检查 A 的证明，发现"假设条件用错了"
- 双方修正后，发现 A 的方法更简洁，但 B 提供了一个关键引理
- 最终方案融合了两者的优势

**优点**：
- 产出多样化的解决方案，避免"思维同质化"
- 自带纠错机制 —— Agent 之间互相找茬
- 特别适合需要"高准确性"的任务（数学、逻辑、代码）

**缺点**：
- **非常昂贵** —— 每轮辩论都要多次 API 调用，成本是顺序模式的数倍
- 可能永远不收敛 —— 两个 Agent 可能陷入"你说我不对，我说你不对"的死循环
- 延迟高 —— 多轮迭代，总时间可能很长
- 需要设计良好的"收敛条件"，否则要么过早停止（方案不够好），要么过晚停止（浪费钱）

**适用场景**：
- 任务有"客观正确"的判断标准（数学题、代码bug修复、逻辑推理）
- 任务对准确性要求极高，值得付出额外成本
- 创意类任务，需要多个角度碰撞（广告文案、设计方案）

#### 4.2.4 模式四：分层式协作（Hierarchical）

**核心思想**：像公司的组织结构，顶层 Coordinator 分配任务给中层 Sub-Agent，中层 Sub-Agent 再调用底层工具或更小的 Agent。

```
                    ┌──────────────────┐
                    │   Coordinator    │
                    │   顶层协调Agent   │
                    │  "我要开发一个App" │
                    └──┬───────┬───────┘
                       │       │
            ┌──────────┘       └──────────┐
            ▼                             ▼
   ┌────────────────┐            ┌────────────────┐
   │ Frontend Agent │            │ Backend Agent  │
   │   前端开发Agent  │            │   后端开发Agent  │
   │  "负责UI和交互"  │            │  "负责API和数据" │
   └───┬────┬───────┘            └───┬────┬───────┘
       │    │                        │    │
       ▼    ▼                        ▼    ▼
   ┌────┐ ┌────┐                ┌────┐ ┌────┐
   │React│ │CSS │                │DB  │ │Auth│
   │工具 │ │工具 │                │工具 │ │工具 │
   └────┘ └────┘                └────┘ └────┘
```

**工作流程**：
1. 顶层 Coordinator 理解用户的大目标（"开发一个App"）
2. Coordinator 拆解为两个子任务：前端开发、后端开发
3. Frontend Agent 负责 UI，它有自己的工具（React 组件生成器、CSS 工具等）
4. Backend Agent 负责 API 和数据库，它有自己的工具（数据库 schema 设计器、认证工具等）
5. 两个中层 Agent 之间可能需要通信（API 格式协商）
6. Coordinator 最终整合两个 Agent 的产出

**这是 Claude Code Subagents 的实际运作方式**。在 Claude Code 中，主 Agent 可以把独立任务分派给 sub-agent —— 每个 sub-agent 拥有独立的上下文、独立的工具权限、独立的任务目标，完成后把结果返回给主 Agent。

**优点**：
- 高度可扩展 —— 增加新模块只需加新的 Sub-Agent
- 模块化 —— 每个 Sub-Agent 独立开发和测试
- 适合非常大的系统（10+ Agent 协作）

**缺点**：
- 架构设计复杂 —— 需要仔细划分层级和职责
- 延迟高 —— 信息要在层级之间传递
- 调试困难 —— 出问题时要在多个层级中排查
- 容易过度设计 —— 大多数场景根本不需要这么复杂的架构

**适用场景**：
- 超大型项目（开发一个完整App、生成一份百页报告）
- 任务可以按"模块"自然划分（前端/后端/数据/设计）
- 可以使用 Claude Code Subagents 或类似框架来简化实现

### 4.3 四种模式对比总览

| 维度 | 顺序式 | 监督式 | 辩论式 | 分层式 |
|------|--------|--------|--------|--------|
| **结构** | 线性链条 | 一管多工 | 多方辩论 | 树形层级 |
| **并行性** | 无 | 中（Worker可并行） | 高（Agent同时生成） | 中（同级可并行） |
| **成本** | 低（N次调用） | 中（1+N次调用） | 高（N×M次调用，M为轮次） | 高（多层级多次调用） |
| **延迟** | 各环节叠加 | Worker并行，综合最快 | 多轮迭代，可能很慢 | 层级传递，中等 |
| **实现难度** | ★☆☆☆☆ | ★★☆☆☆ | ★★★☆☆ | ★★★★☆ |
| **容错性** | 差（单点故障） | 中（Supervisor可重试） | 好（互相纠正） | 中（上级可协调） |
| **最佳场景** | 阶段性工作流 | 可分解的复杂任务 | 需要高准确性的任务 | 超大型模块化项目 |

> 📊 **企业视角：如果你的研发团队已经像多Agent系统一样结构化（清晰的输入/输出/职责边界），那么引入 AI Agent 会非常顺畅。如果不是——AI 转型首先暴露的是组织流程问题。**
>
> **AI Agent 落地成功的企业的共同特征**：
> 1. 工作流程已经被文档化（SOP），每一步的输入输出清晰
> 2. 每个角色的职责边界明确，不会出现"这个事到底谁负责"的模糊地带
> 3. 数据的结构化和标准化程度较高（不是散落在邮件和微信聊天里）
> 4. 有良好的API/MCP基础设施，Agent可以直接调用内部系统
>
> **AI Agent 落地的组织阻力**：
> - 流程不透明 → Agent无法介入（不知道谁做什么、怎么做）
> - 数据未数字化 → Agent"看不到"任何东西
> - 职责模糊 → Agent不知道应该完成到什么程度
>
> **行动建议**：在引入AI Agent之前，先花1-2周做一次"组织流程体检"——把核心工作流画出来，检查每一步是否有清晰的输入/输出标准。这个体检本身的商业价值就很大（通常能发现30%以上的流程冗余），无论你是否引入AI。

### 4.4 多Agent设计原则

无论你选择哪种模式，以下五条原则是通用的：

#### 原则一：为每个Agent定义清晰的职责边界

每个Agent的 system prompt 必须明确回答三个问题：

```
1. 你负责什么？（What is your job?）
2. 你不负责什么？（What is NOT your job?）
3. 你的输出格式是什么？（What format should your output be in?）
```

反面例子（模糊的职责）：
```
你是一个写作助手，帮助用户写好东西。
```

正面例子（清晰的职责）：
```
你是研究员Agent。你的唯一职责是搜索和整理与给定主题相关的资料。
- 你需要做：收集事实、数据、观点、案例，按主题分类整理
- 你不要做：撰写正式文章、评价资料好坏、做最终排版
- 你的输出格式：Markdown结构化笔记，包含"核心概念"、"关键数据"、"不同观点"、"参考来源"四个部分
```

#### 原则二：明确Agent之间的输入/输出Schema

Agent之间的"接口"必须标准化。推荐使用结构化的JSON或固定的Markdown模板，而不是自由格式的文本。

```python
# 好的做法：定义明确的输出结构
researcher_output_schema = """
你必须严格按照以下JSON格式输出：
{
    "topic": "研究主题",
    "key_concepts": ["概念1", "概念2"],
    "data_points": [{"fact": "事实", "source": "来源"}],
    "viewpoints": [{"perspective": "视角", "argument": "论据"}],
    "raw_notes": "详细笔记（自由文本，供Writer参考）"
}
"""
```

**为什么需要Schema？** 因为下游Agent需要可靠地解析上游Agent的输出。如果一个输出字段缺失，下游Agent应该能检测到并报错，而不是继续用不完整的数据工作。

#### 原则三：设定停止条件（Stop Conditions）

多Agent系统必须有"刹车"。没有停止条件的系统会一直运行，烧掉你的API费用。

| 停止条件类型 | 示例 | 适用模式 |
|-------------|------|----------|
| **最大步数** | 辩论最多5轮 | 辩论式 |
| **质量阈值** | Reviewer评分 > 8/10才通过 | 所有模式 |
| **收敛检测** | 两轮输出相似度 > 95% | 辩论式 |
| **超时限制** | 整个流程最多60秒 | 所有模式 |
| **成本上限** | 总token消耗 > 100K则停止 | 所有模式 |

#### 原则四：处理常见异常

多Agent系统中的异常不是"会不会发生"的问题，而是"什么时候发生"的问题：

| 异常类型 | 表现 | 对策 |
|---------|------|------|
| **循环争论** | Agent A 和 B 互相 critique，永远无法达成一致 | 设最大迭代轮次；引入"裁判Agent"做最终裁决 |
| **任务漂移** | Agent 的输出逐渐偏离原始目标 | 每轮把原始任务重新注入prompt；Supervisor定期检查 |
| **上下文膨胀** | 每个Agent的输出都堆叠给下游，总token指数增长 | 中间环节做摘要压缩；只传递关键信息，不传递完整历史 |
| **幻觉放大** | A 编造了一个"数据"，B 基于这个假数据进一步发挥 | 关键事实要求标注来源；Reviewer 专门核查数据的可验证性 |
| **输出格式错误** | Agent 没有按约定的JSON格式输出 | 使用 JSON mode / Structured Output；加解析重试机制 |

#### 原则五：知道什么时候单Agent更好

再次强调本节最重要的原则。以下是单Agent优于多Agent的典型场景：

- 任务简单，单一prompt就能描述清楚（写一封邮件、翻译一段话、回答一个问题）
- 任务不需要"质量审查"环节（用户自己会审）
- 任务有标准答案，不需要多角度思考（数学计算、数据查询）
- 成本预算有限（多Agent的成本是单Agent的N倍）
- 延迟要求高（多Agent的串行延迟不可接受）

#### 案例三：Claude Code Subagents

Claude Code 是当前最成熟的 coding agent 产品之一，它对多Agent的使用堪称教科书级别：

- **主Agent**：与用户对话，理解任务，决定是否拆解
- **Sub-agents**：主Agent可以创建临时sub-agent，每个sub-agent有：

Claude Code Subagents 的设计哲学完美体现了"多Agent是协调问题"这一核心思想：**不是让agent们自由聊天，而是用结构化的任务分发和结果收集来组织协作。**

#### 第一步：初始化 LLM 客户端

```python
"""
============================================================
第一步：初始化 LLM 客户端
============================================================
使用 DeepSeek API（性价比高，适合教学）
你也可以替换为 OpenAI / Qwen / 其他兼容 OpenAI SDK 的 API
"""

from openai import OpenAI

# ========== 配置区：修改为你的 API Key ==========
API_KEY = "your-api-key-here"  # 替换为你的真实 API Key
BASE_URL = "https://api.deepseek.com"
MODEL = "deepseek-chat"
# =================================================

client = OpenAI(
    api_key=API_KEY,
    base_url=BASE_URL
)

def call_agent(system_prompt: str, user_message: str, temperature: float = 0.7) -> str:
    """
    通用的 Agent 调用函数。
    
    参数：
        system_prompt: 系统提示词，定义Agent的"人设"和行为规范
        user_message: 用户消息，即这个Agent要处理的具体任务
        temperature: 创造性参数（0=确定性，1=创造性），默认0.7
    
    返回：
        Agent 的文本回复
    """
    response = client.chat.completions.create(
        model=MODEL,
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": user_message}
        ],
        temperature=temperature,
        max_tokens=4096
    )
    return response.choices[0].message.content

print("✅ LLM 客户端初始化成功！")
```

#### 第三步：构建多Agent流水线

```python
"""
============================================================
第三步：构建多Agent流水线（顺序协作模式）
============================================================
数据流：
  Topic → Researcher → 研究笔记
                      ↓
            Writer ← 研究笔记
                      ↓
                   初稿
                      ↓
            Reviewer ← 初稿
                      ↓
                   审稿意见
                      ↓
            Reviser ← 初稿 + 审稿意见
                      ↓
                   终稿
"""

def run_multi_agent_pipeline(topic: str, verbose: bool = True):
    """
    运行完整的多Agent写作流水线。
    
    参数：
        topic: 文章主题
        verbose: 是否打印详细的中间输出
    
    返回：
        包含所有阶段输出的字典
    """
    results = {"topic": topic}
    
    # ===== 阶段1：研究 =====
    if verbose:
        print("=" * 70)
        print("📚 阶段 1/4：Researcher 正在研究...")
        print("=" * 70)
    
    research_notes = call_agent(
        system_prompt=RESEARCHER_PROMPT,
        user_message=f"请研究以下主题，并按格式输出研究笔记：\n\n{topic}",
        temperature=0.5  # 研究阶段用较低温度，追求准确性
    )
    results["research_notes"] = research_notes
    
    if verbose:
        print(research_notes[:1000] + "\n... (研究笔记完整内容已保存)\n")
    
    # ===== 阶段2：写作 =====
    if verbose:
        print("=" * 70)
        print("✍️  阶段 2/4：Writer 正在撰写初稿...")
        print("=" * 70)
    
    draft = call_agent(
        system_prompt=WRITER_PROMPT,
        user_message=f"""请基于以下研究笔记，撰写一篇初稿。

【研究笔记】
{research_notes}

请按照约定的格式输出初稿。""",
        temperature=0.7  # 写作阶段用中等温度，平衡创造性和准确性
    )
    results["draft"] = draft
    
    if verbose:
        print(draft[:800] + "\n... (初稿完整内容已保存)\n")
    
    # ===== 阶段3：审核 =====
    if verbose:
        print("=" * 70)
        print("🔍 阶段 3/4：Reviewer 正在审核初稿...")
        print("=" * 70)
    
    review_feedback = call_agent(
        system_prompt=REVIEWER_PROMPT,
        user_message=f"""请审核以下初稿，并给出具体的修改建议。

【原始主题】
{topic}

【初稿】
{draft}

请按照约定的格式输出审稿意见。""",
        temperature=0.3  # 审核阶段用更低温度，追求一致性和客观性
    )
    results["review_feedback"] = review_feedback
    
    if verbose:
        print(review_feedback[:800] + "\n... (审稿意见完整内容已保存)\n")
    
    # ===== 阶段4：修改 =====
    if verbose:
        print("=" * 70)
        print("📝 阶段 4/4：Reviser 正在修改...")
        print("=" * 70)
    
    final_article = call_agent(
        system_prompt=REVISER_PROMPT,
        user_message=f"""请根据审稿意见修改初稿，输出最终版本。

【原始主题】
{topic}

【初稿】
{draft}

【审稿意见】
{review_feedback}

请按照约定的格式输出终稿和修改说明。""",
        temperature=0.5
    )
    results["final_article"] = final_article
    
    if verbose:
        print(final_article)
        print("\n" + "=" * 70)
        print("✅ 多Agent流水线执行完毕！")
        print("=" * 70)
    
    return results


# 测试运行
TOPIC = "AI Agent 在工程设计中的应用：现状、机遇与挑战"

results = run_multi_agent_pipeline(TOPIC, verbose=True)
```

### Q1：多Agent一定比单Agent好吗？

**答：不一定。而且大多数情况下，多Agent并不比单Agent好。**

一个设计精良的单Agent，配合一个清晰的system prompt，通常可以达到80-90分的效果。多Agent能把这个分数提到90-95分，但代价是4-10倍的成本和复杂度。你需要判断：多出来的那5-10分，值不值得多花4-10倍的钱和时间？

对于以下场景，**不值得**：写邮件、写日报、翻译文档、回答常见问题、生成简单报告。

对于以下场景，**值得**：正式发表的公众号文章、对外的商业报告、学术论文、需要多方验证的深度研究。

### Q2：如何选择四种协作模式？

按"任务复杂度"和"准确性要求"两个维度来判断：

| 任务复杂度 \ 准确性要求 | 低 | 高 |
|--------------------------|----|----|
| **低** | 单Agent！不要多Agent | 顺序式（加Reviewer把关） |
| **高** | 监督式（并行加速） | 辩论式 或 分层式 |

### Q3：多Agent系统中，Agent之间应该传什么格式的数据？

**推荐 JSON 或结构化 Markdown**。原因：

1. 结构化数据可以被程序解析和验证（字段缺失时可以自动报错）
2. 下游Agent能快速定位到需要的信息（而不是在长文本中搜索）
3. 便于做日志记录和调试（每个字段的变更可追踪）

自由格式的文本只适合简单的Agent间通信。对于生产级系统，一定要定义Schema。

### Q4：我的API费用会因为多Agent翻很多倍吗？

**是的。而且翻的倍数可能超出你的预期。**

具体分析：
- 顺序式：N个Agent，约N倍费用
- 监督式：1个Supervisor + N个Worker，约 N+1 倍费用
- 辩论式：每轮辩论 N个Agent各调用一次，M轮辩论 = N×M 次调用
- 分层式：取决于树的深度和宽度，可能是单Agent的5-10倍

**省钱技巧**：
1. 对不同Agent用不同模型 —— Researcher 可以用便宜的模型（如 DeepSeek），Writer 用强模型
2. 减少不必要的中间输出 —— 如果研究笔记很长（5000+字），先让 Researcher 自己压缩到2000字以内
3. 设置最大token限制 —— 每次API调用设置合理的max_tokens，防止"废话连篇"

### Q5：Agent之间以什么形式"通信"？是发消息还是调API？

这取决于你的实现方式。本节课采用的是**最简单的"数据传递"模式**：上一个Agent的输出作为下一个Agent的输入文本。这是入门阶段最合适的方式。

更高级的通信方式包括：
- **函数调用**：Agent A 调用一个函数，参数中包含任务描述，返回值是 Agent B 的输出
- **消息队列**：Agent 之间通过消息队列（如 Redis、RabbitMQ）异步通信
- **标准化协议**：如 A2A（Agent-to-Agent Protocol），定义了Agent发现的标准化接口
- **共享内存/状态**：如 LangGraph 的 State 对象，所有 Agent 共享同一个状态对象

对于初学者，**从"数据传递"开始**，遇到瓶颈再升级。

### Q6：我写的多Agent系统，Reviewer总是说"写得很好，没有要改的"，怎么办？

这说明 Reviewer 的 prompt 不够"苛刻"。解决方法：

1. **降低 temperature**：把 Reviewer 的 temperature 调到 0.1-0.2，让它的评判更稳定
2. **强制要求找问题**：在 Reviewer prompt 中加一句"你必须找出至少3个可改进的地方，哪怕文章看起来很完美"
3. **细化审核维度**：不要只让 Reviewer "审核文章"，而是拆解为"结构审核、逻辑审核、数据审核、语言审核"四个子维度
4. **给 Reviewer 提供对比标准**：在 prompt 中加入"请以《经济学人》的文章质量为标准进行审核"

### Q7：多Agent和MCP、A2A有什么关系？

三者解决不同层面的问题：

| 概念 | 解决的问题 | 层级 |
|------|-----------|------|
| **多Agent模式**（本节课） | 多个Agent之间如何组织和协调 | 架构设计层 |
| **MCP**（Model Context Protocol） | Agent如何标准化连接外部工具和数据源 | 工具连接层 |
| **A2A**（Agent-to-Agent Protocol） | 不同Agent之间如何发现和通信 | 通信协议层 |

它们可以组合使用：你用**顺序式多Agent模式**组织工作流，每个Agent通过**MCP**连接自己的专业工具，Agent之间通过**A2A**标准化通信。但在入门阶段，先专注于"模式设计"，拿到真切的感受后再逐步引入 MCP 和 A2A。

### Q8（企业）：多Agent系统的引入会不会让团队觉得"要被AI取代了"？

**答**：这是企业引入AI时必须认真对待的组织变革问题。建议策略：1) 从"增强"而非"取代"的叙事出发——强调Agent让员工从"做繁琐的收集整理"升级为"做更有价值的分析和决策"；2) 让团队参与Agent的设计过程——他们最了解工作流，让他们定义"哪些环节AI可以帮忙"，他们就成了Agent的"训练师"而非"被替代者"；3) 先把Agent用于每个人都讨厌的重复性工作（如：填报销单、整理会议纪要）——做出"真香"效果后再扩展到更复杂的场景。

### Q9（企业）：多Agent系统的最小可行团队（MVT）是什么？

**答**：参考 Anthropic 的建议——从最简单的架构开始。对于大多数中小企业：1个核心Agent + 2-3个专业工具 + 1个人工审批节点 = 足以覆盖80%的Agent化场景。不要一开始就设计10个Agent的复杂系统——那通常只是过度设计。经验法则：如果3个Agent搞不定，先反思是不是流程本身需要简化，而不是加更多Agent。

### Q10（企业）：多Agent的月度成本大概多少？如何做预算？

**答**：以DeepSeek API为例（¥1-2/百万token），一个4-Agent系统每天处理50个任务的月度成本约为：4 Agent × 平均2000 token/次 × 50次/天 × 30天 = 12M token/月 ≈ ¥12-24/月（出乎意料地低）。但实际上，加上上下文消耗、重试、长文本输出等因素，真实成本约为估算的3-5倍，即¥50-150/月。即使使用Claude/GPT-4等更贵的模型，月成本也通常在¥500-3000范围内——远低于一个实习生的人力成本。建议：先用DeepSeek等低成本模型跑通流程，确认有效后再评估是否需要升级模型。

## 九、本课金句

> 1. **多Agent的本质是协调，不是魔法。**
> 2. **先用单Agent，实在不行再上多Agent。**
> 3. **一个设计精良的单Agent > 一个设计粗糙的多Agent系统。**
> 4. **Agent的职责边界，比Agent的数量更重要。**
> 5. **没有停止条件的Agent系统，是一个烧钱的无底洞。**
> 6. **多Agent的价值不在于"数量多"，而在于"各司其职"。**
