## 一、当前有哪些「AI 办公自动化」实例？（先看现象）

### 1.1 一个趋势：AI 从"会聊天"走向"能干活"

过去我们熟悉的 AI 大多"困在对话框里"：你问一句，它答一句。但从 2025 年开始，出现了一类新工具——**AI 智能体（Agent）**，它们能像"数字员工"一样，直接接管你每天在用的软件，替你自动干活。

### 1.2 代表实例：OpenClaw（俗称「龙虾」）

**OpenClaw**（名字谐音，被大家戏称为"龙虾"）是这一波里最有代表性的一个：

> 它是一个**开源、本地优先的 AI 智能体执行框架**——本身不是大模型，而是一套给大模型装上"数字手脚"的系统。核心口号：**让 AI 从"只会说"变成"能执行"。**

它的能力可以拆成四层：

| 层 | 作用 | 大白话 |
|---|---|---|
| **大脑** | 接入 GPT / Claude / 通义千问 / Kimi 等大模型做决策 | 谁来"思考" |
| **手脚** | 提供 40+ 工具：读写文件、执行命令、控制浏览器、调 API | 谁来"动手" |
| **记忆** | 本地持久化存储，数据不上云 | 记住做过的事 |
| **渠道** | 对接飞书、钉钉、企业微信、Telegram、Discord 等 50+ 入口 | 在哪里"上班" |

**最吸引人的点：它能在聊天软件里直接工作。** 典型玩法：

- 在飞书/钉钉群里 @ 它，它自动回复、帮你查资料、发通知
- 每天定时（Cron）执行任务，例如"早上 8 点抓新闻 → 总结 → 发到飞书群"
- 一键处理 Excel 数据、整理文件、生成文档
- 通过"技能市场"（ClawHub）安装现成技能：PPT 生成、邮件自动化、数据分析等

```
它的整体架构（记住这张图）：
  大模型（大脑）
      ↓
  OpenClaw（Agent 执行引擎）
      ↓
  Skills 工具（各种技能插件）
      ↓
  聊天平台（微信/飞书/钉钉/Telegram…）
      ↓
  自动化工作流（定时任务、自动回复…）
```

### 1.3 同类工具还有哪些

- **WorkBuddy（腾讯"龙虾"）**：腾讯官方的 AI 原生桌面智能体，免部署、更面向普通用户
- 各种"Claw"系衍生工具，以及 Coze / Dify 等低代码 Agent 平台

> **小结**：不管叫什么名字，它们做的是同一件事——**让 AI 拥有"手脚"，能调用工具、连接外部系统，从而真正替你完成办公任务。**

## 二、这些自动化工具背后的原理（Skills？MCP？）

### 2.1 关键认知：大模型本身是"嘴"，不是"手脚"

大模型（GPT、Claude、Kimi……）再聪明，本质上也只是**根据输入预测输出**的一段程序：

- 它**读不到**你电脑上的文件
- 它**连不上**你的飞书、数据库、日历
- 它**操作不了**你装的软件

所以，让 AI"能干活"的关键，不是换一个更聪明的大模型，而是**给它装上"手脚"**。而"手脚"在技术上主要就是两个东西：

### 2.2 两个核心概念：Skills 与 MCP

| 概念 | 一句话 | 类比 |
|---|---|---|
| **Skills（技能）** | 教会 AI「**怎么做**」 | 给 AI 一本"操作手册" |
| **MCP（模型上下文协议）** | 给 AI「**新的工具**」 | 给 AI 插一个"万能 USB 接口" |

**Skills**：把"该按什么流程做、注意什么格式、有什么坑"写成一份结构化说明文件，AI 看到就会照着执行。它扩展的是 AI 的**知识、流程、规范**。

**MCP**：一套开放标准协议，让 AI 客户端能**标准化地连接外部工具和数据源**（文件、数据库、软件、API）。它扩展的是 AI 的**可执行能力、外部连接**。

龙虾这类工具，本质上就是 **大模型 + Agent 框架 + Skills（技能）+ 渠道接入（部分还支持 MCP）** 组合出来的。

> 读到这里你可能想问：Skills 和 MCP 听起来都像"工具"，到底什么时候用哪个？下一节专门讲清楚。

## 三、Skills 和 MCP 到底有什么区别？

> 本节参考《补充知识 / Skill 与 MCP 的选型与使用范围》。

### 3.1 一句话核心区分

> **Skill 教会 Agent「怎么做」；MCP 给 Agent「新的工具」。**
> - **Skill** = 知识/流程的注入（说明书）
> - **MCP** = 能力的扩展（新器官）

前者是**提示词工程的组织方式**（写 Markdown 就行），后者是**工具连接协议**（要开发并运行一个服务进程）。

### 3.2 本质区别对比表

| 维度 | Skill | MCP |
| --- | --- | --- |
| **本质** | 一段「指令 + 方法论 + 可选脚本」的提示词包 | 一个运行中的服务进程，通过协议暴露工具 |
| **扩展的是** | Agent 的**知识、流程、领域规范** | Agent 的**可执行能力、外部连接** |
| **运行时** | 静态文本，被加载进上下文 | 独立进程，通过 client-server 协议动态调用 |
| **状态** | 无状态 | 可有状态、有连接、有持久化 |
| **给 Agent 什么** | 「遇到这类任务该按什么 SOP 做」 | 「现在你可以调用这个函数 / 读这个数据」 |
| **成本** | 极低，写 Markdown 即可 | 高，需开发 + 部署 + 维护服务 |
| **交付物** | `SKILL.md`（+ 辅助脚本） | MCP Server（代码 + 工具 schema） |

**一句话记忆：Skill 是「说明书」，MCP 是「新器官」。**

### 3.3 什么时候开发 Skill / MCP（决策树）

```
任务缺的是什么？
│
├─ 缺「指导/规范/流程」──▶ 用现有工具就能做，只是不够专业 ──▶ 开发 Skill
│
└─ 缺「执行能力/外部连接」──▶ 继续判断
        │
        ├─ 必须连接外部系统/数据/进程（Agent 沙箱之外）──▶ 开发 MCP
        │
        └─ Agent 自己写脚本/跑命令就能完成 ──▶ 开发 Skill（把脚本附在 SKILL.md 里）
```

**再通俗一点：**

- 缺的是"**知道怎么做**"（流程、格式、规范）→ 写 **Skill**（零成本）
- 缺的是"**物理上做不到**"（连不上数据库、控制不了软件）→ 写 **MCP**（需部署服务）

### 3.4 一个案例对照：驱动 Excel 生成报表

假设底层都有一段 Python 脚本（生成报表），**做成哪种形态取决于包装方式**：

| 形态 | 做法 | 结果 |
| --- | --- | --- |
| **Skill 形态** | `SKILL.md` 写明「用 `python cli.py ...` 生成报表」，Agent 自己执行脚本 | Agent 通过「读说明 + 跑命令」完成任务 |
| **MCP 形态** | 把脚本包装成 MCP Server，暴露 `create_report` / `export_pdf` 等工具 | Agent 直接「调用工具函数」完成任务 |

**判断依据**：
- 如果 Agent 能在自己的沙箱里直接跑 Python 脚本 → **Skill 就够了**。
- 如果脚本必须跑在**特定机器、特定进程、需要保持窗口/会话状态**，而 Agent 运行环境无法直接触达 → **需要 MCP**，让 Server 常驻在那台机器上暴露工具。

### 3.5 两者不互斥，而是组合

最佳实践往往是一起用：

```
MCP Server  ──暴露──▶ 工具（write_cell / add_chart / export_pdf）
                          ▲
                          │ 调用
Skill（SKILL.md）─────▶ 教 Agent「做销售报表该按什么 SOP：先写表头 → 填数据 → 质检」
```

- **MCP 管「能不能做」**（提供器官）
- **Skill 管「做得好不好」**（提供手法）

## 四、Agent 的工作流程：它怎么调用 Skill 和 MCP？

### 4.1 一个关键理解：Skill 和 MCP 都是 Agent 的"工具"

无论是 Skill 还是 MCP，最终都要被 **Agent（智能体）** 在一个循环里用起来。理解这个循环，你就真正理解了"AI 自动化"的运行方式。

### 4.2 Agent 主循环（The Agent Loop）

Agent 的运行本质是不断迭代的 **感知 → 决策 → 执行** 循环：

```
    +----------+    +----------+    +----------+    +----------+
    | OBSERVE  |--> |  THINK   |--> |  DECIDE  |--> |   ACT    |----+
    | 观察     |    | 思考     |    | 决策     |    | 执行     |    |
    +----------+    +----------+    +----------+    +----------+    |
         ^                                                          |
         |                    FEEDBACK（反馈结果）                   |
         +----------------------------------------------------------+
```

一步一步看：

1. **OBSERVE（观察）**：读取当前状态——用户输入、对话历史、上一步工具返回的结果
2. **THINK（思考）**：大模型分析上下文，理解"用户到底要什么"
3. **DECIDE（决策）**：选择下一步行动——调用某个工具？直接回复用户？还是结束？
4. **ACT（执行）**：真正执行——调用 Skill / 调用 MCP 工具 / 运行代码 / 搜索
5. **FEEDBACK（反馈）**：把执行结果写回状态，判断目标是否达成；没达成就回到第 1 步继续

**伪代码长这样：**

```python
def agent_loop(task: str, tools: list, max_iterations: int = 50) -> str:
    messages = [{"role": "system", "content": SYSTEM_PROMPT},   # 系统提示词
                {"role": "user",   "content": task}]            # 用户任务

    for _ in range(max_iterations):
        # ① 观察 + 思考 + 决策：让大模型决定"下一步干什么"
        response = llm.chat(messages, tools=tools)

        # ② 如果它决定直接回复用户 → 任务结束
        if response.has_text_output():
            return response.text

        # ③ 如果它决定调用工具 → 逐个执行
        for tool_call in response.tool_calls:
            result = execute_tool(tool_call)     # 执行工具（可能是 MCP 工具）
            messages.append({"role": "tool", "content": result})  # 结果写回对话

        # ④ 判断目标是否达成，没达成继续循环
        if evaluate_completion(messages, task):
            return final_output
```

> 关键点：**工具调用的结果会再次喂给大模型**，让它"看了结果再决定下一步"——这正是 Agent 区别于"一次问答"的地方。

### 4.3 Skill 和 MCP 分别怎么"接进来"

| 对象 | 怎么被 Agent 用到 |
| --- | --- |
| **Skill** | 被**加载进上下文**。Agent 启动时，把匹配到的 `SKILL.md` 内容读进来；当用户需求命中 `description` 时，Agent 就"照着说明书"一步步执行 |
| **MCP 工具** | 被注册成**可调用工具（Tool）**。Agent 通过工具定义（名称 + 描述 + 参数 JSON Schema）知道"有这么个工具、什么时候该用它"，需要时**发起调用** |

**一个完整例子**（把 Skill 和 MCP 串起来看）：

```
用户："帮我生成本周的销售报表，发到飞书群"

① Agent 识别意图 → 命中 Skill《销售报表生成》（SKILL.md 被加载）
② Skill 告诉它 SOP：先查数据 → 生成图表 → 导出 PDF → 发飞书
③ 执行到"查数据"时，Agent 发现需要连数据库 → 调用 MCP 工具 query_sales()
④ 执行到"生成图表"时 → 调用 MCP 工具 add_chart()
⑤ 执行到"发飞书"时 → 调用 MCP 工具 send_feishu_message()
⑥ 每一步的结果都回传 Agent，最终拼出完整报表并发出
```

> **一句话总结**：Skill 告诉 Agent"**按什么套路走**"，MCP 给 Agent"**走路要用的工具**"，Agent 在循环里把两者结合起来完成整件事。

## 五、回顾：Skills 的开发流程

> Skills 在上一课《Python 基础与 Skills 开发实战》已经讲过，这里快速回顾核心，重点放在"能落地"。

### 5.1 Skill 是什么

**Skill（技能）** = 一个放在特定目录下的**文件夹**，里面至少有一个 `SKILL.md` 文件（带 frontmatter 的结构化 Markdown）。当用户需求触发它时，AI 会自动按里面的规则执行。

```
my-skill/                  ← 技能文件夹（名字用英文/短横线）
├── SKILL.md               ← 技能说明书（核心，AI 读这个）
└── reference/             ← （可选）辅助文件：模板、示例
    └── weekly-report-template.md
```

### 5.2 SKILL.md 的核心结构

```markdown
---
name: weekly-report            # 技能名称（唯一标识）
description: 当用户需要生成周报时使用，生成结构化的中文周报   # 触发描述（最关键！）
---

# 周报生成技能

## 何时使用
当用户说"写周报""生成周报""总结本周工作"时使用。

## 执行步骤
1. 收集信息：本周完成事项、遇到的问题、下周计划
2. 按结构输出：标题 / 一、本周完成 / 二、问题与解决 / 三、下周计划
3. 输出 Markdown

## 示例
输入：本周做完了实验数据处理，下周开始写论文
输出：（给出一个完整周报示例）
```

**frontmatter 两个字段**：
- `name`：技能名字（英文短横线式，唯一标识）
- `description`：**最关键**——写清楚"什么时候用这个技能"，AI 靠它判断何时触发

### 5.3 好 Skill 的三个标准

1. **触发清晰**：description 写清楚"当用户提到 XX 时使用"
2. **步骤明确**：1→2→3 可执行，不模棱两可
3. **有示例**：给出"输入→输出"示例，AI 会模仿

### 5.4 最核心的技巧：让 AI 帮你写 Skill（元技能）

> **你不需要自己从零写**。直接对 AI 说下面这段话，它就能帮你生成一个 Skill：

```
请帮我创建一个技能（Skill），要求：
1. 功能：把一段口语化的会议记录整理成结构化的会议纪要
2. 输出格式：标题、参会人、结论、待办事项（带负责人）
3. 触发条件：当用户说"整理会议记录""生成会议纪要"时使用
请生成 SKILL.md 文件内容
```

AI 会生成结构完整的 `SKILL.md`，你保存成文件即可使用。**写 Skill = 会写需求说明。**

## 六、实战：MCP 如何开发（详细）

这是本课重点。我们从一个最小例子入手，再做一个贴合"办公自动化"的完整实战。

### 6.1 MCP 的核心概念（先建认知）

MCP（Model Context Protocol，模型上下文协议）是一套**标准协议**，规定"AI 客户端"和"工具服务器"之间怎么对话。

```
┌─────────────┐       MCP 协议       ┌──────────────────┐
│  AI 客户端   │  ◀──────────────▶  │  MCP Server      │
│ (Claude/IDE) │    JSON-RPC 通信    │  (你写的工具服务) │
└─────────────┘                      └──────────────────┘
```

核心概念（记不住没关系，先混个脸熟）：

| 概念 | 是什么 | 类比 |
| --- | --- | --- |
| **Host** | 你正在用的 AI 应用（Claude Desktop、IDE 插件、自建 Agent） | 用 USB 设备的人 |
| **Client** | Host 内部的协议组件，负责和 Server 对话（一个 Host 可连多个 Server） | 设备上的 USB 接口 |
| **Server** | 你开发的工具服务进程 | 插在电脑上的 USB 设备 |
| **Tool** | Server 暴露给 AI 调用的具体函数（执行动作） | 设备的功能按钮 |
| **Resource** | Server 暴露给 AI 读的数据/文件（只读上下文） | 设备里的数据 |
| **Prompt** | 可复用的提示词模板（给 AI 的固定套路） | 设备的快捷设置 |
| **Transport** | 通信方式（stdio / Streamable HTTP） | USB 线还是无线 |

> 注意：严格来说，**MCP 是 Client 与 Server 之间的通信协议**——Host（AI 应用）负责承载交互与模型调用，Client 负责和 Server 说话，Server 负责把能力暴露出来。完整链路在 6.7 展开。

### 6.2 最小 MCP Server（热身：会"加法和打招呼"的服务器）

先装依赖（Python 生态最流行的是 `mcp` 库的 `FastMCP` 写法）：

```bash
pip install mcp
```

**服务端代码 `server.py`：**

```python
from mcp.server.fastmcp import FastMCP

# ① 创建 MCP 服务器，给它起个名字
mcp = FastMCP("demo")

# ② 用 @mcp.tool() 装饰器，把普通函数"变成"可被 AI 调用的工具
@mcp.tool()
def add(a: int, b: int) -> int:
    """计算两个数的和"""          # ← 这个 docstring 会被 AI 看到，用来判断"何时调用"
    return a + b

@mcp.tool()
def greet(name: str) -> str:
    """向指定的人问好"""
    return f"你好，{name}！"

# ③ 启动服务器，用 stdio 方式通信（标准输入输出）
if __name__ == "__main__":
    mcp.run(transport="stdio")
```

**关键点（读 MCP 代码就抓这三处）：**

1. `FastMCP("名字")` → 创建服务器对象
2. `@mcp.tool()` + **函数的 docstring** → 工具的名字、说明、参数由**类型注解 + docstring 自动生成**，AI 靠它理解"这个工具能干啥"
3. `mcp.run(transport="stdio")` → 启动并选择通信方式（`stdio` = 标准输入输出，本地调试最常用）

> 注意：MCP Server **不会自己主动干活**，它只是"坐在那里等着被调用"。真正调用它的是 AI 客户端（下一小节讲怎么连）。

### 6.3 教学实战：一个「待办事项管理」MCP（贴合办公自动化）

上个小例子太"玩具"。现在做一个真正有用的办公工具：**让 AI 帮你管理待办事项**（增、查、完成），数据持久化到本地 JSON 文件。

**为什么选这个例子**：贴合办公场景（任务管理）、纯本地无外部依赖、能演示"工具 + 状态持久化"两个核心点，学生能立刻跑通。

**完整代码 `todo_server.py`：**

```python
import json
import os
from mcp.server.fastmcp import FastMCP

# ① 创建服务器
mcp = FastMCP("todo-server")

# ② 数据文件：待办事项存在这个 JSON 文件里（持久化，重启不丢）
DATA_FILE = "todos.json"

# ③ 辅助函数：读文件（文件不存在就返回空列表）
def load_todos():
    if not os.path.exists(DATA_FILE):
        return []
    with open(DATA_FILE, "r", encoding="utf-8") as f:
        return json.load(f)

# ④ 辅助函数：写文件
def save_todos(todos):
    with open(DATA_FILE, "w", encoding="utf-8") as f:
        json.dump(todos, f, ensure_ascii=False, indent=2)

# ⑤ 工具1：新增待办
@mcp.tool()
def add_todo(text: str) -> str:
    """新增一条待办事项，参数 text 是待办内容"""
    todos = load_todos()
    todos.append({"text": text, "done": False})
    save_todos(todos)
    return f"已添加待办：{text}（当前共 {len(todos)} 条）"

# ⑥ 工具2：查看全部待办
@mcp.tool()
def list_todos() -> str:
    """列出当前所有待办事项"""
    todos = load_todos()
    if not todos:
        return "暂无待办事项"
    lines = []
    for i, t in enumerate(todos, start=1):
        mark = "[已完成]" if t["done"] else "[未完成]"
        lines.append(f"{i}. {mark} {t['text']}")
    return "\n".join(lines)

# ⑦ 工具3：完成某条待办
@mcp.tool()
def complete_todo(index: int) -> str:
    """把第 index 条待办标记为已完成"""
    todos = load_todos()
    if index < 1 or index > len(todos):
        return f"无效序号：请传入 1 到 {len(todos)} 之间的数字"
    todos[index - 1]["done"] = True
    save_todos(todos)
    return f"已完成：{todos[index - 1]['text']}"

# ⑧ 启动
if __name__ == "__main__":
    mcp.run(transport="stdio")
```

**从这个例子你看到 MCP 工具开发的完整套路**：

1. **想清楚工具清单**：提供几个工具？每个工具的输入（参数）、输出（返回值）是什么？
2. **写普通 Python 函数**：每个工具就是一个函数，`@mcp.tool()` 一贴就"变"成工具
3. **docstring 写明白**：一句话说清这个工具干什么、参数什么意思（AI 靠这个决定是否调用）
4. **状态自己管**：要持久化就自己读写文件/数据库，Server 是"有状态"的

### 6.4 MCP Server 的完整开发流程（七步）

```
① 需求分析 ──▶ 想清楚"要提供哪几个工具"
② 环境准备 ──▶ pip install mcp
③ 写代码   ──▶ 用 FastMCP + @mcp.tool() 写工具（可让 AI 帮你生成）
④ 本地测试 ──▶ 用 mcp 官方调试工具手动调用，确认每个工具正常
⑤ 配置接入 ──▶ 在 AI 客户端里登记这个 Server（给名字 + 启动命令）
⑥ 联调验证 ──▶ 用自然语言对话，看 AI 是否自动调用工具
⑦ 部署运行 ──▶ 需要长期可用时，部署成常驻进程 / 远程服务
```

### 6.5 怎么"接上"AI 客户端（以配置 JSON 为例）

Server 写好后，要在 AI 客户端里"登记"，客户端才知道有这么个工具服务器。典型配置长这样：

```json
{
  "mcpServers": {
    "todo": {
      "command": "python",
      "args": ["todo_server.py"],
      "cwd": "/path/to/your/project"
    }
  }
}
```

配置后重启客户端，AI 就会多出 `add_todo`、`list_todos`、`complete_todo` 三个工具。此时你对 AI 说：

> "帮我把『明天下午交周报』加到待办，然后列出所有待办。"

AI 会自动调用 `add_todo` 再调用 `list_todos`，你就能看到结果——**这就是一个最小但完整的"AI 办公自动化"闭环。**

### 6.6 开发 MCP 的常见坑

| 坑 | 说明 | 解决 |
| --- | --- | --- |
| **docstring 没写清** | AI 不知道工具何时用、参数什么意思 | 每个工具写清"干什么 + 参数含义" |
| **参数类型不明确** | 缺类型注解，schema 生成错误 | 用 `text: str`、`index: int` 标注 |
| **stdio 与 SSE 混淆** | 本地调试用 stdio，远程服务才用 SSE | 默认 stdio 即可 |
| **忘记持久化** | 数据只存内存，重启就丢 | 需要保留就用文件/数据库 |

### 6.7 深入：MCP 的完整架构（Host / Client / Server）

上面我们只用了"Client ↔ Server"。真实世界里还有一个常被忽略的角色：**Host**。

| 角色 | 说明 |
| --- | --- |
| **Host** | 用户使用的 AI 应用（Claude Desktop、Cursor、IDE 插件、自建 Agent 平台） |
| **Client** | 位于 Host 内部，负责与 Server 建立会话、交换协议消息；**一个 Host 可连多个 Server** |
| **Server** | 开发者主要编写的部分，把文件读取、SQL 查询、GitHub 查询等能力暴露给 Host |

> **关键区分**：MCP 协议只发生在 **Client 和 Server** 之间。Host 是"用的人"，Client 是"传话的"，Server 是"干活的"。Server 背后的数据源（本地文件、数据库、第三方 API）不属于协议角色。

**一次 MCP 调用的完整流程**：

```
模型发现自己缺数据（如 Git 日志）→ 生成工具调用
        │
        ▼
Host 把调用交给 MCP Client
        │
        ▼
Client 通过 JSON-RPC 请求 Server
        │
        ▼
Server 执行查询，结果沿原路径返回
        │
        ▼
模型据此组织回答
```

**初始化握手（最容易忽略）**：正式调用工具前，Client 和 Server 先"互相认识"——

1. Client 发 `initialize` 请求（带上自己支持的协议版本、能力列表）；
2. Server 返回自己支持的版本、能力、基础信息；
3. Client 再发 `initialized` 通知，双方进入可用状态。

> 排查"Server 配好了但工具没出现"时，**先看初始化阶段是否失败**——协议版本不匹配、SDK 版本不一致是最常见原因。

**Server 能暴露三类东西**（凉拌黄瓜比喻）：

| 能力 | 是什么 | 比喻 |
| --- | --- | --- |
| **Tools** | 执行动作（查询、发送、创建、修改） | 切菜、拌料、开火 |
| **Resources** | 只读上下文（文件、日志片段、数据库 Schema） | 冰箱里有什么食材 |
| **Prompts** | 可复用的提示词模板（如"按团队规范做代码审查"） | 家里的固定口味偏好（少放辣、必放香菜） |

> 大多数 Server **先只提供 Tools 就够了**；需要只读上下文或固定套路时再加 Resources、Prompts。另外还有三个更高级的 **Client 侧能力**，了解即可（取决于客户端是否实现）：**Roots**（Host 告诉 Server"允许在哪些目录内工作"）、**Sampling**（Server 请 Host 的模型帮忙生成一段内容）、**Elicitation**（Server 执行中回头向用户补充询问信息）。

### 6.8 深入：MCP 的底层协议与通信方式

**为什么用 JSON-RPC 2.0？**

- REST 偏"资源"（`/users/1`、`/orders/100`）；
- JSON-RPC 偏"方法调用"（`tools/call`、`resources/read`）；
- AI 工具调用天然是"我要执行某个动作"，所以 JSON-RPC 更贴合。

请求示例：

```json
{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": {
    "name": "read_file",
    "arguments": { "path": "/path/to/file.txt" }
  },
  "id": 1
}
```

成功响应只返回 `result`，失败响应才返回 `error`（**不要在成功响应里再塞 `error: null`**）：

```json
{ "jsonrpc": "2.0", "id": 1, "result": { "content": [ { "type": "text", "text": "文件内容..." } ] } }
```

> 工具参数用 JSON Schema 描述——它既是运行时校验规则，也是给模型的"说明书"。

**两种通信方式**：

| 方式 | 特点 | 适合 |
| --- | --- | --- |
| **stdio** | Server 作为子进程启动，通过 stdin/stdout 交换消息；无网络部署成本 | 本地工具、个人使用（默认推荐） |
| **Streamable HTTP** | 统一端点（`POST /mcp`），认证、负载均衡可沿用普通 HTTP 运维 | 团队服务、远程 API、多用户访问 |

> ⚠️ **stdio 模式最大的坑**：stdout 是协议消息通道，**不能拿来打印调试日志**！一行 `print()` 就可能破坏消息格式。调试日志请写到 stderr 或文件。
>
> 协议版本在持续演进（当前稳定版为 2025-11-25 revision），接入前确认协议 revision 与 SDK 版本即可。

### 6.9 生产级 MCP：工具设计、安全与运维（进阶）

办公自动化场景下，AI 要操作你的文件、数据甚至发消息——**安全不能靠"相信模型"**。把 Server 做进生产环境，至少注意四件事：

**① 工具设计：避免"万能工具"**

❌ 反面（操作范围和权限都丢给模型猜）：

```python
execute_sql(sql)                    # 模型想执行什么 SQL 都行
file_operation(op, path, data)      # 读写删改一把梭
call_api(url, method, body)         # 任意 URL 随便请求
```

✅ 正面（按业务动作拆分，权限和校验落在每个具体工具上）：

```python
get_user_by_id(id)                  # 只查一个用户
list_active_orders(user_id)         # 只列订单
read_file(path)                     # 只读
write_report(path, content)         # 只写报告
```

- 工具名用"**动词 + 名词**"；
- `description` 写清适用条件、必填参数和**禁用场景**；
- 大文件：单个 chunk 约 100KB，超过 10MB 只返回说明和可选读取方式，别让模型一次吃整个文件。

**② 权限与安全清单**：

| 检查项 | 要求 |
| --- | --- |
| 路径遍历 | 读文件前做路径规范化，禁止 `../` 越出允许目录 |
| SQL 注入 | 用参数化语句，绝不把模型生成的字符串直接执行 |
| 数据脱敏 | 手机号、邮箱、Token、密钥等返回前脱敏 |
| 写操作 | 删除/修改/发送默认收紧权限，设人工确认 + 审计 |
| 第三方 Server | 接入前审核源码、依赖和权限 |

**③ 可观测性**：每次请求有 Trace ID；工具调用的参数、耗时、结果、错误码有结构化日志；能还原"Agent 回答背后调用过哪些工具"；有超时、限流、熔断、重试。

**④ 成本归因与依赖治理**：每次调用能关联到用户/业务线/工具/会话；Token 与 API 成本可拆分统计；有配额与预算告警；模型循环调用工具要有次数上限；SDK/第三方库/第三方 Server 要有维护者和更新记录。

> **一句话**：MCP 只改变了"工具的接入方式"，**不会替代鉴权、审计、日志、版本、限流**——这些和普通后端服务没有本质区别。

### 6.10 本节小结：MCP 到底解决了什么？

把 JavaGuide 的总结翻译成一句话：

> **MCP 解决的是"外部工具和数据源如何接入 AI"这件事**。它让同一个工具（如 Git、数据库、WPS 桥接层）写一次，任何支持 MCP 的 Host 都能发现并调用——这就是"接入一次、处处可用"。
>
> 但 MCP **不负责**：模型怎么决定调用（Function Calling）、任务怎么编排（Agent）、请求是否被授权（业务安全）。这三件事各有各的层。

**进阶阅读**：JavaGuide《什么是 Model Context Protocol (MCP)？和 Function Calling、Agent 什么关系？》→ https://javaguide.cn/ai/agent/mcp.html

## 七、实战进阶：在 Agent 中自动化真实软件（以 WPS 为例）——仅 Skills + MCPs 够吗？

> 到这里，你已经会写 Skill、也会写 MCP Server 了。但注意：前面我们自动化的都是"Agent 自己够得着的东西"（文件、数据、JSON）。如果目标是**自动化真实软件**——WPS、Excel、飞书、浏览器——仅靠 Skills 和 MCPs 够吗？本节用两份真实工程文档（《补充知识/WPS技术文档.md》《补充知识/Excel-Agent可视化操作工具开发文档.md》）来回答这个问题。

### 7.1 先做个思维实验：让"当前 Agent"驱动 WPS

假设你对着正在使用的 Agent（CodeBuddy / Claude Code 这类 IDE Agent）说：

> "用 WPS 生成一份 8 页的汇报 PPT，套用蓝色商务风，导出 PDF。"

Agent 会怎么做？它天生自带一堆"手脚"：读文件、写文件、执行命令、搜索网页……但它**物理上没有控制 WPS 的能力**——它不知道 WPS 的界面，也没有 WPS 的"遥控器"。

你可能会说：写 Python 脚本呗，`python-pptx` 不是能生成 PPT 吗？——对，但 `python-pptx` 只是**直接拼出一个 .pptx 文件**，并没有真正驱动"WPS 这个软件"，更做不到"套用 WPS 里保存的模板"。

> **关键认知**：要自动化真实软件，必须有**一条连接 Agent 与软件进程的通道**。Skills 和 MCPs 都不是这条通道本身——它们只是通道两端约定好的"说明书"和"插座"。通道（也就是真正操作软件的那层代码）需要我们自己开发。

### 7.2 通道长什么样？答案藏在 WPS 技术文档里

先看真实工程的架构图（摘自《补充知识/WPS技术文档.md》第 3 节）：

```
┌─────────────────────────────────────────────┐
│  Skill 层   skills/SKILL.md                 │ ← AI Agent 调用协议（说明书）
├─────────────────────────────────────────────┤
│  CLI 层     wps_cli.py / __main__.py        │ ← 命令行入口（Agent 跑命令即可调用）
├─────────────────────────────────────────────┤
│  业务层     core/*.py                       │ ← 语义化 API（impress / writer / calc）
├─────────────────────────────────────────────┤
│  规范层     styles/*.py                     │ ← 设计预设 / 布局模板 / 质量检查
├─────────────────────────────────────────────┤
│  工具层     utils/repl_skin.py              │ ← REPL 交互界面（人也能用）
├─────────────────────────────────────────────┤
│  后端层     utils/wps_backend.py            │ ← COM 调度（真正的"遥控器"！）
├─────────────────────────────────────────────┤
│  WPS Office（Kwpp / Kwps / Ket Application）│ ← 实际软件
└─────────────────────────────────────────────┘
```

注意最下面三层：真正"捅进" WPS 的是**后端层**——它通过 Windows 的 **COM 接口**（一种"软件遥控协议"，把软件内部操作暴露成可编程命令）向 WPS 进程发送"新建文档、添加幻灯片、设置字体"等指令。

配套的 Excel 项目（《补充知识/Excel-Agent可视化操作工具开发文档.md》）把这个思想讲得更直白，它的目录就是一套**最小组件集**：

```
excel-agent/
├── backend.py          # COM 后端（唯一接触 win32com 的层）← 遥控器
├── core/excel_doc.py   # 语义化 API（ExcelDoc：write / style / add_chart...）← 按钮
├── core/quality.py     # 质量检查（空单元格、列宽过窄检测）← 质检员
├── cli.py              # CLI 入口 ← 快捷指令
├── example.py          # 端到端示例
├── skills/SKILL.md     # Agent 技能定义 ← 说明书
└── requirements.txt    # pywin32>=306
```

**核心原则就一句话：只有 `backend.py` 接触底层接口（win32com），其余所有层都只跟"自己的 API"打交道。**

### 7.3 拆解：一个"软件自动化"工程需要哪些组件？

| 组件 | 作用 | 类比 | 必须？ |
| --- | --- | --- | --- |
| **后端层（Backend）** | 唯一与软件进程通信的层（COM / SDK / CDP / UI Automation） | 遥控器 | **必须** |
| **语义 API 层（Core）** | 把底层命令包装成 `add_slide()`、`write_cell()` 这种好懂的函数 | 遥控器上的按钮 | **必须** |
| **CLI 层** | 命令行入口：`python cli.py --new --write A1 值 ...` | 快捷指令 | 强烈建议 |
| **会话管理（Session）** | 管理软件进程的启动/关闭，防止进程残留 | 用完关电源 | 强烈建议 |
| **Skill（SKILL.md）** | 告诉 Agent"什么场景用什么命令、按什么 SOP 做" | 使用手册 | **必须**（面向 Agent） |
| **MCP 包装层** | 把语义 API 包成 MCP Server，暴露成工具 | 万能插座 | 按需 |
| **规范/质量层** | 设计预设、布局模板、溢出检测等"成品质量"保障 | 质检员 | 可选 |

> **结论**：Skills 和 MCPs 只是**最上层的"协议 / 说明书"**。真正让软件动起来的是**后端层 + 语义 API 层**——这才是"还需要开发的组件"，也是软件自动化项目里工作量最大、最需要小心设计（资源回收、错误处理）的部分。

### 7.4 回到问题：仅仅 Skills 和 MCPs 够吗？分场景看

| 场景 | 例子 | 够不够 | 为什么 |
| --- | --- | --- | --- |
| ① Agent 沙箱内能自己搞定 | CSV 整理成表格、批量改文件名、生成 Markdown 周报 | ✅ **Skill 足够** | Agent 自带"读写文件 + 执行命令"，Skill 只负责教它怎么做 |
| ② 需要操作本机 GUI 软件 | 驱动 WPS/Excel 生成 PPT、导出 PDF | ⚠️ **Skill + 桥接层** | Skill 管流程、MCP 可选，但**必须有后端层代码**能碰到软件进程 |
| ③ 跨机器 / 常驻 / 多人共享 | 服务器上的数据库、公司内部系统、远程设备 | ⚠️ **必须上 MCP** | Agent 运行环境够不到，需要 Server 常驻在目标机器上暴露工具 |

**一句话总结**：
- **Skill 解决"知不知道怎么做"，MCP 解决"Agent 与外部世界按什么协议连"，但它们都不解决"怎么物理操作某个软件"**。
- 操作软件的那层代码（COM / CDP / UI Automation 桥接）必须自己开发，开发完再决定：
  - 包成 **CLI 脚本** → 由 Skill 说明书指挥 Agent 去跑；
  - 或包成 **MCP Server** → 由 Agent 直接调用工具。

### 7.5 三种"接法"对比：同一套底层代码的三种包装

| 接法 | 包装方式 | Agent 怎么用 | 适合 |
| --- | --- | --- | --- |
| **接法 A：CLI + Skill** | 写 `cli.py`，再写 `SKILL.md` 教 Agent 跑命令 | "读说明书 → 执行命令" | 本机、单人、快速落地（本课推荐） |
| **接法 B：MCP Server** | 把语义 API 包成 MCP Server，暴露 `create_ppt` 等工具 | 直接"调用工具" | 常驻服务、跨机器、多人共享 |
| **接法 C：组合** | Skill 教 SOP + MCP 提供工具 | "按流程调用工具" | 复杂任务，最专业 |

> 判断依据（与《补充知识/Skill与MCP的选型与使用范围.md》一致）：Agent 能直接跑通 → 优先 Skill；必须常驻在特定机器/进程才能触达 → 才上 MCP。

### 7.6 从 WPS 技术文档学到的 6 个工程要点

1. **单一后端隔离**：COM 调用集中在 `backend` 一层，上层无底层依赖 → 以后想换实现（LibreOffice、python-pptx）只改一处。
2. **规范与内容解耦**：`styles/` 管"长什么样"，`core/` 管"放什么内容"，两者互不纠缠。
3. **质量内建**：生成后自动跑 `quality_checks`（文本溢出、越界、字号过小），让"生成即检查"成为默认流程。
4. **面向 Agent 双入口**：`SKILL.md` + CLI 两种入口，既可由人手动调用，也可被 AI Agent 驱动。
5. **资源生命周期可控**：用 `Session`（上下文管理器）管理 WPS 进程，任务结束自动 `Quit`，避免进程泄漏——这对 GUI 软件自动化尤其重要。
6. **多格式交付**：一份内容可导出 PPTX / PDF / PNG 序列，满足汇报、归档、预览不同场景。

### 7.7 完整的 Agent 视角：一次 WPS PPT 自动化全程

把"人说话 → 软件产出"串起来看：

```
用户："生成 8 页蓝色商务风汇报 PPT，导出 PDF"
  │
① Agent 识别意图 → 命中 Skill《WPS-PPT 生成》（SKILL.md 被加载进上下文）
② Skill 给出 SOP：选设计预设 → 逐页填充 → 质量检查 → 导出
③ Agent 执行 `python -m cli_anything.wps ...`（走 CLI 层）
④ CLI → 业务层 API → 后端层 COM → WPS 进程：新建/排版/填内容/导出
⑤ 质量检查发现问题（文本溢出）→ Agent 修正后重跑
⑥ 导出 PDF / PNG 序列交付
```

这个过程中各组件各司其职：
- **Skill** 负责"① 意图识别 + ② SOP 指导"；
- **CLI（或 MCP）** 负责"③ 调用入口"；
- **后端层**负责"④ 真正操作软件"；
- **质量检查**负责"⑤ 返工闭环"——这正是第四节"Agent 循环"在软件自动化中的实际应用。

### 7.8 小结：本节一张图

```
        ┌──────────────────────────────────────┐
        │  Agent（大脑 + 默认手脚：读写/执行命令） │
        └──────────────────────────────────────┘
                      │ ① 命中并加载
        ┌─────────────▼─────────────┐
        │  Skill（说明书 / SOP）      │ ← 已有能力，只需写 Markdown
        └─────────────┬─────────────┘
                      │ ② 指挥执行
        ┌─────────────▼─────────────┐    ┌─────────────────┐
        │  CLI / MCP（调用入口）      │←─┤  MCP Server（常驻）│
        └─────────────┬─────────────┘    └─────────────────┘
                      │ ③ 调用
        ┌─────────────▼─────────────┐
        │  语义 API（Core）           │ ← 需要开发的组件 ①
        └─────────────┬─────────────┘
                      │ ④ 翻译成软件命令
        ┌─────────────▼─────────────┐
        │  后端层（COM / CDP / UIA）  │ ← 需要开发的组件 ②（最关键）
        └─────────────┬─────────────┘
                      │ ⑤ 操作
        ┌─────────────▼─────────────┐
        │  真实软件（WPS / Excel…）   │
        └───────────────────────────┘
```

> **回答本节问题**：仅靠 Skills 和 MCPs **不够**。Skill 管"怎么做"，MCP 管"怎么连"，但"物理上操作软件"还得靠你自己开发的**后端桥接层 + 语义 API**。好消息是：这个工作量是**一次性**的——做好一次，配一个 `SKILL.md` 说明书，任何 Agent 都能复用这套能力。

### 7.9 拓展：理论上能否自动化"所有"软件？

学完上面 8 小节，你肯定会冒出这个问题：既然只要写一层桥接就能自动化 WPS，那是不是**所有软件**理论上都能自动化？——答案是：**几乎可以，但有前提**。严谨的说法是：

> **只要软件存在"可编程通道"，就能自动化；通道的质量决定了自动化能有多可靠、多便宜。**

#### ① 核心逻辑：所有自动化都靠一条"通道"

WPS 用的是 COM 接口，但"通道"不止这一种。按**稳定性与工程成本**从优到劣，可以排成一张金字塔：

| 通道类型 | 原理 | 稳定性 | 例子 |
| --- | --- | --- | --- |
| ① 官方 SDK / API | 软件官方提供的编程接口 | 最稳 | 飞书开放平台、微信机器人 |
| ② COM / OLE | 系统级组件对象模型 | 很稳 | WPS、Office、AutoCAD |
| ③ 命令行（CLI） | 进程内直接执行 | 很稳 | Git、FFmpeg、Python |
| ④ 网络协议 | 抓包复现 HTTP/WebSocket 请求 | 较稳 | 网页后端接口 |
| ⑤ 浏览器 CDP | DevTools 协议控制浏览器 | 较稳 | Playwright 控制任何网页 |
| ⑥ UI Automation | 读取无障碍树、操作界面控件 | 中等，随版本易变 | 老式桌面软件 |
| ⑦ 模拟鼠标键盘 + OCR | 图像识别 + 坐标点击 | 最脆弱、最慢 | 实在没有接口的"最后手段" |

**结论**：只要软件不是"只有像素、没有任何可编程入口"的黑盒，理论上都能自动化——哪怕只剩屏幕，也能用第⑦层"图像识别 + 模拟点击"硬上。这也是为什么很多自动化工具（如按键精灵）靠"录屏回放"也能工作。

#### ② 但"能自动化" ≠ "值得自动化"

三个现实约束会打折扣：

1. **反自动化 / 安全机制**：验证码、人机校验、设备指纹、风控——这类是**故意**不让你自动化的（银行 App、游戏、部分政务系统）。
2. **真人强校验**：人脸识别、短信验证码、需要真人身份的场景，自动化只能"半程"。
3. **实时强交互判断**：3D 建模、音视频精修这类需要人眼反复判断的活儿，模拟点击既慢又容易错，自动化收益很低。

#### ③ 一句话结论

> 理论上：**有通道就能自动化，通道越底层越"万能"但越脆弱**。
> 实际上：先看软件给了哪级通道（①~⑦），再判断有没有反自动化/真人校验，最后**算一笔账**——接一条通道要写一次桥接层，且随软件更新要持续维护。

这也是为什么现实世界里只自动化"**高频 + 接口友好**"的软件（Office/WPS、浏览器、企业协作工具），而不是"什么都自动化"。

### 7.10 案例：抖音 / 快手——"接口被焊死"的典型

#### ① 为什么没人敢自动化短视频平台？

对照 7.9 的通道金字塔，抖音/快手是**接口友好度最低**的一类软件，要分两层看：

| 层面 | 有没有接口 | 说明 |
| --- | --- | --- |
| 官方开放平台 | 有，但"窄" | open.douyin.com / open.kuaishou.com 提供内容发布、数据统计、商业化 API，但**只面向企业创作者运营**，且**没有用户侧"自动点赞/评论/私信"接口** |
| 用户操作层 | 基本没有 | 刷、赞、评、私信、直播互动等操作没有官方接口，只能走非官方通道 |
| 个人可用检索 API | 没有 | 官方**没有**向个人开放"关键词搜索全站视频"的接口 |

非官方通道只剩三条路（对照 7.9 的金字塔），**全部被风控封堵**：

| 通道 | 现实 |
| --- | --- |
| ⑤ 浏览器 CDP（网页版） | 滑块验证、设备指纹、行为检测，短时间就封 |
| ⑥⑦ 手机 UI 自动化 + OCR | "养号、自动回复、自动弹幕"灰产做法，成本高、封号快 |
| ④ 抓包逆向私有协议 | 平台明令禁止，签名/加密不断升级，且**有法律风险** |

所以正规 MCN 都是"官方 API + 人工运营"，没有公司做"全自动运营"的合规产品。

#### ② 那"只查找筛选、零互动"呢？有接口吗？有风险吗？

这是学员最容易踩的**"安全错觉"**：**只读 ≠ 零风险**。

- **官方**：依旧没有个人可用的全站检索 API。
- **非官方**：
  - 网页版搜索 + 浏览器自动化只读结果——"最轻"，但仍违反平台条款；
  - 抓包复现搜索接口——效率高，但**绕过了平台访问控制，性质不同**。

风险分三层：

| 风险 | 说明 |
| --- | --- |
| ① 平台条款 | 用户协议禁止"未经授权抓取数据"，**只读也违约**，平台可随时封 IP/封号 |
| ② 风控封禁 | 搜索频率一高 → 滑块验证、设备指纹、限流，严重者账号拉黑 |
| ③ 法律 | 只读少量 → 主要是民事（不正当竞争，参考"微博诉脉脉""大众点评诉百度"等判例）；**大规模抓取 + 绕过签名/验证码** → 情节严重可能触及"非法获取计算机信息系统数据罪"；涉及作者个人信息再加工，还可能违反《个人信息保护法》 |

**判断能不能做的四个关键变量**：规模（抓多少）、频率（多快）、是否绕过防护（技术上"撬锁"没有）、用途（自用研究 vs 商用）。

合规替代方案：

| 需求 | 合规做法 |
| --- | --- |
| 关键词热度 / 趋势 | 巨量算数（抖音系）、磁力引擎（快手系）——官方数据产品 |
| 视频数据聚合分析 | 飞瓜数据、新榜等第三方数据服务商的商业授权 |
| 相对开放的平台 | B站、YouTube 等有更开放的数据接口，合规压力小 |

#### ③ 本节启示

> **接口友好度决定了自动化的"能"与"不敢"**：WPS/Excel 把接口递到你手里，所以人人能自动化；抖音/快手把接口焊死，所以连"只读检索"都要掂量风险。**判断能不能做，看的是"官方有没有给口子"和"规模频率是否可控"，而不是"我没点赞就没事"。**

这个案例也是对 7.3 组件清单的补充：**先查通道（官方 API 有没有、开到哪一层），再决定要不要写桥接层**——通道根本不存在时，写再好的桥接层也是白费。

## 八、总结：当前简单工作流的缺点与后续改进

到目前为止，我们搭的是一个"**单 Agent + 手动触发 + 串行工具调用**"的简单工作流。它够入门，但离真正的"自动化"还有明显差距。

### 8.1 当前工作流的缺点

| # | 缺点 | 具体表现 |
| --- | --- | --- |
| 1 | **要人手动触发** | 每次都得人发一句话才动，没做到"定时/事件自动跑" |
| 2 | **单 Agent 能力有限** | 任务一复杂（多目标、多工具、多步骤）就容易"迷路"、顾此失彼 |
| 3 | **工具调用是"串行试探"** | 缺规划，边做边试，效率低、易反复 |
| 4 | **Skill 是静态文本** | 不能感知运行环境/中间状态，遇到变化不会自适应 |
| 5 | **会"失忆"** | 上下文窗口有限，长任务越跑越忘前面做过的决策 |
| 6 | **缺反思纠错** | 工具返回错误时，往往不会停下来修正，而是硬着头皮继续 |
| 7 | **安全与权限风险** | AI 自主执行（写文件、发消息、跑命令）一旦失控，缺沙箱/审计 |

### 8.2 后续改进方向（引出后续课程）

```
简单工作流  ──────────────▶  进阶工作流
─────────────────────────────────────────────
手动触发        ──▶  事件驱动 + 定时调度（Cron、触发器）
单 Agent        ──▶  多 Agent 协作（编排者 + 执行者分工）
串行试探        ──▶  规划 + 反思（Plan-and-Execute、ReAct）
静态 Skill      ──▶  动态技能 + 记忆注入
无记忆          ──▶  短期/长期记忆系统（向量检索）
无安全防护      ──▶  沙箱隔离 + 权限控制 + 审计日志
```

这些正是后续要学的内容：**工作流编排框架（LangGraph / CrewAI）、记忆系统、多 Agent 架构、事件驱动自动化、安全与评测**。

> **本课小结一句话**：龙虾这类工具 = 大模型 + Agent 循环 + Skills（怎么做的说明书）+ MCP（能做什么的工具）。你现在已经能动手开发其中最关键的两块——Skill 和 MCP。
